01

场景故事

复杂问题的答案质量，取决于检索规划而不是生成文采

多跳问题的困难在于：第一步检索之前，你往往不知道该搜什么。传统单次检索 RAG 把「搜什么」固化在用户查询里，跨文档证据遗漏、结论无法溯源。推理中检索（Search-o1 路线）把搜索变成推理循环里的动作：模型在每一步显式暴露不确定性，自主改写查询继续搜索，再判断证据是否足够。

本项目的生产模块 code/ragdeep 实现了这条控制流：五阶段状态机（INITIAL 初始分析 → SEARCHING 搜索中 → READING 文档阅读 → REASONING 推理中 → COMPLETED 已完成）驱动主链；检索回的长文档先做语义切分、压缩与证据对齐（Reason-in-Documents 思路），结构化证据单元再回注主推理链。LLM 与检索函数都是注入参数，换模型或换检索源不动控制流。

诚实地说，当前检索源是 mock_search：5 篇内置文档上的关键词匹配，不是真实搜索引擎。这意味着控制流本身是真实可运行的、可插拔 LLM 的，但任何「检索质量提升了多少」的说法都必须等接上真实检索源并重跑实验之后才有资格出现。本页严格执行这条边界。

可迁移场景：法律尽调证据核验、医疗文献循证问答、电商竞品与行业研究。

07

面试深挖预演

为什么要推理中检索？单次检索 RAG 的失败模式是什么？
单次检索假设问题信息完整，但多跳问题在第一步检索后才知道该搜什么。典型失败包括查询与真实信息需求错位、检索结果互相矛盾、长文档稀释关键证据。推理中检索把搜索作为推理循环里的动作，按需触发、按需改写。
你说控制流是真的，检索是假的，这算实现完了吗？
算一半，而且是明说的那一半。状态机、不确定性触发、查询改写、证据注入是完整可运行的代码，LLM 与检索函数都是注入参数，这一点有 27 项单测背书。检索质量结论需要真实检索源，这条边界写在页面第一屏。面试里主动划这条线，比被问出来体面得多。
信息饱和怎么判断？模型自评可靠吗？
设计上是模型自评加硬预算双闸：连续无新增证据则停止，并设最大检索次数。诚实地说，自适应早停（模型自判停止）还是计划补齐项，当前代码里只有硬预算。所以现在跑出的任何循环都归因于预算控制，不是模型学会了停。
文档内推理和直接把检索结果塞进上下文有什么区别？
直接输入长文档会稀释注意力且引用不可追溯。文档内推理先做语义切分和压缩，把主张与证据对齐成结构化证据单元，主链只接收压缩后的证据，引用可以回溯到原文位置。
这个项目和 m1 的 RAG 是什么关系？R71 是你的成绩吗？
不是。R71 那组 HotpotQA 小样本评测走的是 m1 的检索内核，归属企业知识库问答页。本项目与 m1 的关系是控制流复用与互补：m1 是单次检索的生产检索栈，本项目是多轮规划的控制流骨架。归属规则是「证据归脚本真正导入的代码路径」，这套纪律本身也是面试可讲的。
接真实检索源要做什么？为什么现在不接？
search_fn 换成真实搜索 API，另外补查询改写对 API 语义的适配和限流重试。控制流已经就位，接源本身工作量可控；真正的工作量在接源之后的评测集建设与重跑，在那之前任何质量数字都是空气，所以排期上先把评测口径立住。

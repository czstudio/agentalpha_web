01

场景故事

从「模型能答」到「真的查过」：单 Agent 工具调用的三个工程件

模型流畅地答完一个问题，不代表它真的查过数据。「我以为调过了」是工具调用事故的常见根源：模型只生成了任务单（Generated），系统才真正执行（Executed），两个谓词混淆之后，缺参、超时、权限三类故障就会被同一种「再试一次」耽误。

这个项目把契约做进 ReAct 循环：思考产出「动作+参数或 Finish」，观察必须真实返回并写回上下文；步数用 max_iterations=8 硬约束，防止无限循环。失败回退分两类：未知工具返回带可用工具列表的错误提示，工具执行异常被捕获后作为观察写回，循环继续推理而不是整单崩溃。

六个行情工具（股价、公司信息、历史走势、股息、对比、财务指标）全部基于 yfinance 真实接口实现，并已抽成统一适配层（unified_stock_adapter.py），单 Agent 与多 Agent 研报产线共用同一套工具契约。合规上只提供客观数据分析，不做投资建议、不预测股价。

可迁移场景：HR 制度问答、智能工单分派、运维告警处置。

07

面试深挖预演

为什么不用 LangChain 的 AgentExecutor？
框架的价值在生态，代价是循环细节变成黑盒。手写循环只有几十行，Thought 解析、工具分派、异常回退、步数约束每一行都可讲。面试官问「循环怎么退出」「解析失败怎么办」，手写版可以直接翻到对应行。
缺参和工具报错为什么处理方式不一样？
未知工具名说明模型对工具表的理解错了，返回带可用工具列表的提示让它自我纠正；工具执行异常说明环境或数据有问题，把错误信息作为观察写回，让模型决定换工具还是换参数。两者都不该用无限重试掩盖。
max_iterations=8 这个数怎么定的？
行情速查问题通常 2 到 4 次工具调用就能回答，8 步留了纠错余量又不放任循环烧 token。这是步数墙不是性能指标：撞墙即失败并留痕，方便统计步数合规率。
数据是真实的还是 mock 的？
六个工具全部基于 yfinance 真实接口（stock_tools.py 里逐一可查），这也是真实运行轨迹还没上线的原因：连真实数据源就有网络与限流问题要处理，评测产物要等真实运行入库后才写。固定值夹具只用于锁定行为边界的单元测试。
什么时候该从单 Agent 拆成多 Agent？
三个信号：工具过载、审查需要独立上下文、子任务异构。本项目到多 Agent 版（研报工厂）的拆分点就是把「查」和「审」分成不同角色，两边共用统一工具适配器。
这个项目的诚实边界在哪？
评测数字一条都没有：路由正确率、步数合规率都是已定义口径、未运行的规划项。页面上把「代码事实」和「评测成绩」分栏，就是为了不在面试里把设计当成绩讲。

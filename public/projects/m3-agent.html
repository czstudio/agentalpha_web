01

场景故事

从调用 API 到实现上百轮工具调用的稳定性：应用层 Agent 的五个核心组件

模型流畅地答完了——但没调工具、没查数据、没验事实。「我以为调过了」是所有工具调用事故的根：模型只生成任务单（Generated），系统才执行（Executed），两个谓词混淆，缺参/超时/权限三种病就会被同一招『重试』耽误。

这个项目把契约做进循环：思考产出『动作+参数或 Finish』，观察必须真返回且写回；错误三分类——模型层错改任务单不重试、瞬时错误限次重试 K=3、确定性错误停。缺 city 参数的观察是『缺少必填参数』而不是异常栈；`pow` 被枚举拦在重试循环外。

金融场景加四道闸：入口门闩拒预测股价（工具环 0 次）、先查再比（两次独立观察）、失败句禁 or-0 兜底、出口『非投资建议』声明。8 工具场景下角色路由把「搜一下销量」从单路选错（0.75）修到全对（1.0）——何时拆多 Agent 的决策点。

可迁移场景：HR 制度问答、智能工单分派、运维告警处置。

08

面试深挖预演

为什么错误要分三类？
缺参说明参数填写有误，需要修改后重发。超时属于环境抖动，可以原样重试 K=3 次。权限不足或除零属于确定性失败，需要停止执行。如果将这些情况统称为重试，会导致用重试的方法处理参数修改问题，从而引发更多错误。
反思和『再检查一遍』有什么区别？
让模型再检查一遍属于同一分布的续写，模型同时担任了生成者和检查者。独立批评器只提交问题列表，每条包含维度、问题和修改方法。如果谓词条件设置过窄，错误依然会被放行。我们在终稿中保留了对『快很多』的漏扫，10 分代表达到了规则的满分标准，并不代表完全没有瑕疵。
什么时候该拆多 Agent？
拆分多智能体有三个信号：工具过载，其中近义工具比正交工具更容易引发错误；审查环节需要独立的上下文；子任务包含异构指令。如果工具数量少且不重叠，或者流程较短，就不需要拆分。多 Agent 架构会带来 15× token 的消耗成本。
MOCK 数据会不会被问穿？
JD 要求的是契约与稳定性设计。MOCK 用于锁定行为边界，例如将 AAPL 190.0 和 MSFT 410.0 锁死，后续更换 yfinance 时只需要更换数据源层。构建测试夹具先行体现了基本的工程素养。
合规四闸最容易被忽略哪个？
输出时需要进行出口声明，如果回答完不加声明，陈述的内容会被用户当成建议。『MSFT 市值更大（非投资建议）』中的括号不是装饰，而是划分责任边界的标识。
AutoGen 学到什么？
类名仅代表名称，协议的核心在于 MayExec 的执行主体。在 0.2 版本中由 Assistant 负责规划，Proxy 负责执行，到了 0.4 版本则把工具收进 Assistant。虽然设计在变化，但职责分离的核心问题保持不变。
这个模块和 workflow 何时二选一？
当分支可枚举且流程确定时，适合使用 workflow，这种方式成本较低且易于审计。当需要模型自主决策动作序列时，适合使用 Agent。如果选择错误，会导致浪费 token 或无法实现预期能力。

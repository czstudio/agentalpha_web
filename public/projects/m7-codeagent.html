01

场景故事

给 Agent 一个带 bug 的仓库和一个任务描述，让它自己看代码、定位、修改、跑测试

EvoAgent 基于 mini-swe-agent 基座构建：Agent 在沙箱内浏览仓库结构、检索相关函数、编辑补丁；评测走 minisweagent 的 bench 入口（run_bench_cli），FixBench 与 Terminal-Lite 两套任务族分别考「仓库修复」与「终端操作」。

定位句先说准：FixBench 是 SWE-bench 风格的合成仓库修复任务，以 pytest 退出码判定 resolved；它不是 SWE-bench 本身，也不是真实 GitHub issue。所有主数字的实验条件是 Qwen2.5-Coder-7B-Instruct、temperature 0、单次运行、n=20 或 n=40，区间宽是样本量的诚实代价。

这个项目最有面试价值的部分反而是负结果：把「修法沉淀成技能库」的卖点放进对照实验后，开技能库的两臂都比不开低（9/20 与 25/40），McNemar 检验不显著；自进化闸门 23 轮全部回滚、0 个候选被接受。技能库最终沉淀 48 条、3 代进化 fitness 0.6325→0.6351，涨幅如实报微弱。

可迁移场景：企业内部代码库问答助手、自动化 CR 机器人、测试修复流水线。

写进简历怎么写

基于 mini-swe-agent 构建代码修复 Agent 并完成两组基准评测：FixBench 12/20（60%，Wilson CI 0.39-0.78）、Terminal-Lite 27/40（67.5%，CI 0.52-0.80），Qwen2.5-Coder-7B、temperature 0、单次协议

08

面试深挖预演

FixBench 60% 放什么坐标系里看？
三个坐标：它是合成修复任务，不是 SWE-bench Verified，不能和公开榜比；n=20 的 Wilson 区间是 0.39 到 0.78，宽 39 个百分点，只约束「管线能跑、判分可信」，不约束精确水平；同任务 1.5B 模型 0/20，说明任务对模型能力敏感。三个坐标一起讲，比单报 60% 可信。
技能库不是你的卖点吗？为什么效果是负的？
对，这就是这个项目最诚实的部分：把卖点放进对照实验，开技能库的两臂都更低（9/20、25/40），McNemar 和 Holm 校正后全部不显著。可能的原因是检索注入的技能占上下文预算、命中率与任务相关性强。负结果照登且进统计表，这是给自己攒的信用：说明其余正结果不是挑出来的。
GateClimb 的闸门怎么工作？拦对了还是拦错了？
三道闸：G1 训练集未超过基线即回滚，G2 留出余量带，G3 才接受。实际跑了 23 轮全部停在 G1，0 个候选被接受。诚实说：没有「坏补丁被拦、好补丁被放」的对照集，所以只能证明闸门在拒绝，不能证明拒绝都拒对了。这句话原文写进了页面和审计。
自建评测集怎么防止「出题出歪了」？
EvalForge 三段验收：第一段可构建、参考解能过；第二段错解必拒；第三段余量带（基线通过率必须落在区间内才接受）。seed 77 那批生成 32 题，第一段 32/32，第三段只放行 5 题、拒绝 27 题。闸门厚一点没关系，评测集比模型成绩优先。
下一步怎么把技能库做成正增益？
先归因：424 次检索 327 次命中说明复用发生了，但发生在不涨分的任务上。方向是把技能注入从「按相似度 top-k」改成按任务族条件触发，并把上下文预算让给当前任务；再用留出集复测。这是假设，不是结论，页面不会把它写成已有成果。
为什么不用 SWE-bench Verified 直接测？
成本与环境是现实约束，但更重要的是页面纪律：没有跑过的基准不写分数。SWE-bench Verified 列在评测口径里明确标「未跑、不写」，这比放一个来源不明的百分比体面。

01

场景故事

企业遗留系统维护场景：issue 进、verified patch 出

给 Agent 一个带 bug 的真实仓库和一个 issue 描述，让它自己看代码、定位文件、改代码、跑测试、交补丁——这是 Code Agent 的完整闭环，也是 SWE-bench 评测的任务形态。

项目基于 mini-swe-agent 基座构建：Docker 沙箱隔离执行环境，Agent 在沙箱内浏览仓库结构、检索相关函数（调用图/依赖图辅助定位）、编辑补丁；生成的 patch 进入自研评测管线（log 解析 + grading），在 SWE-bench Verified 与 SWE-smith 上计算 resolve rate。

关键对比实验：「从零生成」vs「仓库复用」——同样的修复任务，Agent 利用仓库内已有工具函数与从零写新代码，在成功率与 token 消耗上的差异。

可迁移场景：企业内部代码库问答助手、自动化 CR 机器人、测试修复流水线

09

面试深挖预演

SWE-bench 的任务是怎么组织的？resolve 怎么判定？
每个 instance = 仓库快照 + issue 描述 + 失败测试。Agent 提交 patch 后在干净环境里跑 FAIL_TO_PASS 测试（修复前失败、修复后应通过）和 PASS_TO_PASS（不能改坏），全过才算 resolved。
Agent 定位 bug 靠什么？纯靠模型看文件吗？
基线靠文件树浏览 + grep；增强路线是结构化索引——函数调用图、依赖图把「issue 关键词 → 相关函数」的搜索变成图上的邻域查询。仓库复用实验证明定位质量直接决定修复成功率。
沙箱为什么用 Docker？安全边界在哪？
Agent 会执行任意命令，必须隔离：文件系统、网络、进程都限制在容器内。课程项目还配了 bubblewrap（轻量 namespace）和 swerex 等多种执行后端，按隔离强度与启动开销取舍。
从零生成 vs 仓库复用，你的实验结论是什么？
仓库复用在「仓库内已有相似逻辑」的任务上成功率高、token 省；但检索错误时会引入无关依赖反而失败。结论：复用策略要和定位置信度挂钩。
失败样本你怎么分析的？
按四个桶归类：定位错文件、编辑正确但引入新问题、测试未过、预算超限。每个桶给典型样本与改进方向——这份分析比 resolve rate 本身更能体现工程能力。
你的 resolve rate 要放什么坐标系里看？
SWE-bench Verified 上有两类公开锚点：代码专用模型（快手 KAT-Dev-72B-Exp 74.6% 开源纪录）和 MoE 通用模型（美团 LongCat-Flash-Chat 60.4%）。我们的子集分数在这两个锚点之间讲，比孤零零报数字有说服力——基准的意义就是坐标系。
上下文工程具体做了什么？（字节 JD 原词）
四件事：文件树摘要的 token 预算分配、命令历史滑窗压缩、检索片段去重、系统提示与任务提示分层。每个都有消融证据（上下文四档消融实验），不是话术。

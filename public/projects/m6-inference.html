01

场景故事

从「一条请求」到「一个服务」：企业私有化部署的真实工程问题

模型上线的第一课：单条请求的延迟好看没用，并发一上来服务就崩。这个项目从「一条请求」走到「一个服务」：用 vLLM 部署开源模型，开启连续批处理让新请求插队进正在计算的 batch，用 PagedAttention 把 KV cache 显存碎片压到最低。

在此之上做两层优化：推理层试推测解码（小模型草拟、大模型验证）；模型层做量化（GPTQ/AWQ/SmoothQuant、INT4/FP8），用可控的精度损失换显存和吞吐。每一层都配对照压测：不同并发档位下的吞吐、P50/P99 延迟、显存占用，全部出表。

最后搭可观测性：吞吐/延迟/显存三个维度的实时监控，让「服务还能不能扛」变成一个看得见的问题。

可迁移场景：边缘设备部署、多模型混部推理平台、RAG 系统的推理底座

09

面试深挖预演

KV cache 显存怎么算？一台 24G 卡跑 7B 模型能撑多少并发？
权重约 14GB（FP16），剩余给 KV：每层每 token 的 KV 大小 = 2 × kv_head 数 × head_dim × 精度字节，乘层数乘序列长度。用 GQA 的模型 KV 小一个数量级。算出单序列 KV 后除可用显存即最大并发——这个现场推导必须熟练。
Continuous batching 和 static batching 的本质区别？
static：凑一批一起算，最长的请求拖着整批；continuous：迭代级调度，每步之后完成的请求退出、新请求插入，GPU 不空转。收益在请求长度方差大的负载上最明显。
推测解码什么时候失效？
草稿模型接受率低的时候：大模型频繁否决草稿，验证开销反而吃掉收益。难生成（代码结构性强的分布）接受率低，开放文本高。Medusa 用多头并行草拟缓解单草稿模型的串行瓶颈。
AWQ 和 GPTQ 的区别？
GPTQ 逐层最小化量化误差（Hessian 加权），AWQ 根据激活分布保护重要权重通道（等价缩放），通常 AWQ 对话类任务更稳、GPTQ 迭代更快。SmoothQuant 把激活异常难度转移到权重侧，适合 W8A8。
你压测的瓶颈在哪一层？怎么定位的？
看指标组合：GPU 利用率高但吞吐不涨 → 调度/批大小问题；利用率低 → 请求不足或内存带宽瓶颈；显存 OOM → KV 容量不足。用 nvidia-smi + vLLM 指标（running/waiting 队列）交叉定位。
MoE 模型的推理部署和稠密模型有什么不同？
总参数装满显存但单 token 只激活一部分（LongCat-Flash-Chat：560B 总参、激活 18.6-31.3B）。并行策略多一个 EP（专家并行）——EP 切专家、TP 切矩阵；4090 跑 MoE 吃亏因为总参装不下且 EP 要多卡。美团官方部署参数：FP8 + flashinfer attention + EP-MoE + TP8（单机 H800，100+ tok/s）。
为什么选 vLLM 而不是 SGLang 或 TensorRT-LLM？
三个维度：生态与迭代速度（vLLM 社区最快）、radix cache 与结构化解码（SGLang 强项）、kernel 极致性能与商用卡绑定（TensorRT-LLM，腾讯混元采用）。我选 vLLM 的主因是它与 veRL rollout 引擎同源——训练侧复用同一套栈，这个理由比「教程用的」硬。

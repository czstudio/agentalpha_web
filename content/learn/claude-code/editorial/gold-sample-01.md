# 第 1 章：Claude Code 到底在做什么？从一句需求到一次代码修改

如果你用过聊天机器人，大概已经习惯了这样的节奏：问一个问题，等一段回答，然后自己复制代码、找到文件、运行测试。

Claude Code 少了中间这几次“搬运”。它运行在终端里，可以查看当前项目、修改文件、执行命令，再根据测试结果继续处理。你给它的不是一道问答题，而是一件需要在项目里完成的事。

这一章不急着背命令。我们只做一个很小的任务：修复登录失败后的提示文字。走完以后，你会真正明白 Claude Code 能看见什么、它如何一步步工作，以及为什么最后仍然需要你做决定。

> **这一章结束时，你应该能独立完成：**进入一个已有项目，让 Claude Code 先调查、再修改、最后用代码差异和测试结果检查这次修改。

## 从一个看得见的小问题开始

假设我们有一个练习项目 `tiny-login-app`。现在的规则是：密码连续输错三次，账号会暂时锁定。但页面每次只显示“登录失败”，用户不知道自己还剩几次机会。

我们希望把第一次输错后的提示改成：

```text
登录失败，还可尝试 2 次
```

这是一项很适合第一次练习的任务。目标看得见，修改范围不大，结果也容易检查。

先在终端进入项目，再启动 Claude Code：

```bash
cd tiny-login-app
claude
```

`cd` 后面的文件夹非常重要。Claude Code 会从你启动它的位置了解项目：这里有哪些文件、代码怎样组织、项目提供了哪些命令。这个位置通常叫“工作目录”。白话一点，它就是这次任务摆在 Claude Code 面前的桌面。

![Claude Code 从当前文件夹开始认识项目](/images/learn/claude-code/01-foundations/01-project-desk.png)

*图 1：从项目目录启动后，Claude Code 才能搜索、阅读和修改这套项目里的文件。*

如果你在错误的目录启动，它看到的就可能不是你想改的项目。所以第一次对话可以先问：

```text
先不要修改代码。告诉我这是一个什么项目，主要使用什么技术，应该怎样运行测试。
```

这里的“先不要修改”不是客套。它把第一步限制为调查。你可以先看它找到了哪些配置文件、读了哪些说明，再决定是否继续。

## 第一句任务应该怎么说？

很多人第一次会输入：“帮我优化一下登录。”

这句话的问题不是不够专业，而是没有可判断的终点。“优化”可能是换颜色、改接口、加验证码，也可能是重写整套登录逻辑。Claude Code 即使开始动手，你也很难判断它是否理解正确。

我们把任务写得具体一些：

```text
登录连续失败时，页面一直只显示“登录失败”。
我希望前两次失败后同时显示剩余尝试次数，第三次仍按现有规则锁定账号。

先找出相关实现和测试，告诉我准备改哪些文件，暂时不要修改。
不要改变锁定规则，也不要添加新依赖。
```

这段话没有复杂的“提示词技巧”，只是交代了四件事：

- **现象**：现在看见了什么问题；
- **目标**：用户最终应该看见什么；
- **范围**：先调查，不立即修改；
- **限制**：哪些现有行为不能改变。

![一个可执行任务由现象、目标、范围和限制组成](/images/learn/claude-code/01-foundations/03-prompt-anatomy.png)

*图 2：任务越具体，Claude Code 越容易知道从哪里开始，也越容易知道何时停下。*

你不需要一开始就猜出文件名。找文件本来就是它可以承担的工作。你真正需要说清楚的是业务现象和完成条件，因为这两件事不能由工具替你决定。

### 为什么先让它调查，不直接改？

在陌生项目里，同一句提示可能来自前端组件、后端接口，也可能由多语言文件统一管理。直接要求修改，Claude Code 仍然会搜索，但你会在它已经准备动手时才发现方向不对。

先调查有两个好处：

1. 你能提前看见它对项目的理解是否正确；
2. 它可以把大任务变成几项具体修改，让你更容易发现遗漏。

理想的调查结果应该像这样：

```text
我找到了两处相关代码：

1. src/auth/login.ts 计算失败次数和剩余次数
2. src/components/LoginForm.tsx 显示错误提示
3. tests/login-form.test.tsx 已覆盖账号锁定，但没有覆盖剩余次数

我建议先补一个失败测试，再修改提示内容，不改变锁定条件。
```

这是示例输出，实际文件名取决于你的项目。重点不是它说得多像专家，而是它能指出真实文件，并让后续步骤能够被检查。

## 它和普通聊天窗口最大的区别是什么？

普通聊天窗口可以给你一段代码，但通常不知道这段代码放进项目后发生了什么。Claude Code 可以继续读取文件、编辑代码并运行测试。测试如果失败，它还可以把错误信息当作下一步线索。

官方文档把这个过程概括为三个动作：收集信息、采取行动、验证结果。只要目标还没有达到，这一轮就会继续。

![Claude Code 在查找、修改和验证之间循环](/images/learn/claude-code/01-foundations/02-agent-loop.png)

*图 3：失败的测试会回到下一轮，帮助 Claude Code 判断还需要修改哪里。*

这就是“Agent”最值得理解的地方。Agent 不是一个更会聊天的名字，而是一种工作方式：模型不只生成文字，还会选择工具，并根据工具返回的真实结果决定下一步。

放到我们的登录任务里，一轮可能是这样的：

1. 搜索“登录失败”出现在哪些文件；
2. 阅读失败次数的计算逻辑；
3. 新增一个描述期望提示的测试；
4. 运行测试，先看到测试失败；
5. 修改提示组件；
6. 再运行测试，确认新旧测试都通过。

为什么要故意先看到一次失败？因为它证明新测试确实抓住了当前缺少的行为。如果测试一写完就通过，可能是项目本来已经实现了这个功能，也可能是测试根本没有检查到我们关心的内容。

## 它怎么知道应该先打开哪个文件？

Claude Code 并不是一启动就把整个项目完整记进脑子。真实项目可能有成千上万个文件，把它们全部读一遍既慢，也会混入大量无关内容。

它通常会先寻找入口。入口可能来自你的描述，也可能来自项目本身：

- 你说了“登录失败”，它可以先搜索这段文字；
- 你提到某个页面，它可以从页面组件继续追踪调用；
- 项目的 `package.json`、`pyproject.toml` 等配置会告诉它怎样启动和测试；
- `README.md` 或 `CLAUDE.md` 可能记录项目约定和常用命令；
- 测试文件会展示项目如何描述现有行为。

搜索到候选文件后，它才会读取其中与任务有关的部分，再沿函数调用或变量名称继续寻找。这个过程很像人在陌生仓库中排查问题，只是文件搜索和内容读取由工具完成。

这也解释了为什么任务描述里的具体名词很有用。“登录页面显示错误提示”比“系统有点问题”提供了更多入口；完整报错文字、接口名称、页面路径和复现步骤，都能缩短寻找范围。

如果你已经知道入口，不妨直接告诉它：

```text
问题出现在 /login 页面。后端响应已经包含 remainingAttempts，
请从 LoginForm 组件开始检查，不要重新设计接口。
```

如果你不知道，也不用假装知道。可以让它先给出搜索路径：

```text
先告诉我你会用哪些关键字寻找这个提示，
找到候选文件后再解释它们之间的关系。
```

这里有一个需要尽早建立的习惯：不要只看它最后的结论，也要看结论指向的文件是否真实存在。它说“问题在前端组件”，至少应该能给出组件路径；它说“已经有测试”，应该能指出测试名称。具体位置越清楚，你越容易发现它是否走偏。

Claude Code 在对话里能持续使用的信息也不是无限的。任务很长时，早期细节可能被压缩，所以关键约束不要只在开头随口提一次。发现它准备违反“不要改后端”时，及时重申限制，比等任务结束再追责更有效。后面的章节会专门解释上下文窗口和压缩，这里先记住：对话能延续，不等于每个细节会永远保持同样清晰。

## 现在让它动手，但把顺序说清楚

调查方向没问题后，可以继续：

```text
按刚才的方案修改。
先补测试并运行一次，让我看到它为什么失败；再修改实现，最后运行相关测试。
```

接下来你会看到 Claude Code 读取和编辑文件，也可能看见它准备运行类似下面的命令：

```bash
npm test -- login-form
```

不用死记这个命令。不同项目可能使用 `pnpm test`、`pytest`、`go test` 或其他工具。前面先让 Claude Code调查项目，就是为了让它使用这套项目本来提供的命令，而不是凭空猜一个。

如果测试第一次出现类似结果：

```text
Expected: 登录失败，还可尝试 2 次
Received: 登录失败
```

你已经得到一条很有用的信息：测试准确复现了问题。实现修改后，它应该再次运行同一测试，并让这条失败消失。

### Claude Code 为什么有时会停下来问你？

因为“读一个文件”和“删除文件、安装软件、发布线上版本”不是同等级的动作。

Claude Code 有权限控制。只读调查通常风险较低；修改文件、运行某些命令时，界面可能要求确认；涉及更高风险的操作，你更应该先看清命令和影响范围。

![不同动作需要不同程度的确认](/images/learn/claude-code/01-foundations/04-permission-stop.png)

*图 4：是否需要确认，取决于动作会改变什么，而不是对话进行到第几步。*

看到确认提示时，不要形成“总是允许”的肌肉记忆。先读三个地方：

- 它准备执行什么命令；
- 命令会作用于哪个目录或环境；
- 如果执行错了，是否容易恢复。

例如运行当前项目的测试通常容易判断；删除目录、推送代码、操作生产数据则完全不同。Claude Code 可以解释它准备做什么，但是否接受后果，仍然是你的决定。

> **一个简单原则：**可以恢复、影响范围清楚的动作，可以在看懂后确认；涉及账号、密钥、线上发布、数据删除的动作，不要只凭一句解释就放行。

## 它说“完成了”，我们该看什么？

任务结束时，最容易犯的错误是看到“已完成”就直接关闭终端。

我们至少要看两样东西：代码差异和测试结果。

`diff` 是修改前后代码的差别。它回答“到底改了什么”：有没有碰到无关文件，有没有顺手删除内容，提示文字是否与需求一致。

测试回答另一个问题：“项目运行后，期望的行为真的出现了吗？”一个修改可能看起来合理，却因为变量取错、边界条件遗漏而无法工作。

![代码差异和测试结果检查不同问题](/images/learn/claude-code/01-foundations/05-two-checks.png)

*图 5：diff 检查修改范围，测试检查运行结果；两者不能互相替代。*

可以让 Claude Code 做最后一次收尾：

```text
请总结这次修改：
1. 改了哪些文件，每个文件为什么要改；
2. 运行了哪些测试，结果是什么；
3. 还有哪些没有验证。
```

然后自己快速查看差异和测试输出。你不需要逐字符重做它的工作，但要确认任务最初约定的三件事：前两次显示剩余次数，第三次仍然锁定，没有添加新依赖。

如果它只运行了一个新测试，还应该问一句：“原有的登录相关测试是否也通过？”新功能正确，不代表旧行为一定没有被破坏。

## 如果它走错方向，需要重新开始吗？

不需要。Claude Code 工作时，你可以随时补充信息或纠正方向。

比如它准备同时修改前端和后端，但你知道后端已经返回了剩余次数。这时直接说：

```text
先停一下。后端响应里已经有 remainingAttempts，
不要修改接口，只检查前端为什么没有显示这个字段。
```

这比等它全部改完再返工更省时间。把 Claude Code 当成正在操作项目的搭档，你发现关键事实时就应该及时告诉它。

如果你不确定它的方向，可以把动作退回到调查：

```text
暂时不要继续修改。列出目前已改内容、仍未确认的判断，
以及下一步准备读取或运行什么。
```

注意，这里的重点不是让它写一篇长报告，而是把未知的地方暴露出来。例如“我假设剩余次数来自前端本地计算”就是一项需要查证的判断；“测试已通过”则应该对应一条你能看到的测试结果。

Claude Code 还会为文件修改保留检查点，你可以回退它对代码文件的编辑。不过，检查点不是万能撤销键：它不能自动撤回已经发出的邮件、已经发布的版本、已经写入远端数据库的数据。凡是会离开本地项目的动作，都要在执行前想清楚，而不是把恢复寄托在事后回退上。

### 什么时候应该先用 Plan 模式？

这次登录提示很小，先调查再修改已经够用。遇到下面这些情况，可以先进入 Plan 模式：

- 你对项目不熟，不知道修改会波及哪些模块；
- 任务涉及数据库、权限或部署，做错后的代价较高；
- 你只想让它分析方案，不希望它立刻改变文件。

Plan 模式的作用很朴素：先让 Claude Code 阅读和思考，把“准备怎么做”摆出来，再由你决定是否进入实现。它不会让方案自动变正确，所以仍然要检查方案是否遗漏了业务条件。

## 哪些工作适合交给它，哪些不能含糊？

Claude Code 很适合承担“目标明确、能在项目里找到线索、结果可以检查”的任务。例如修一个能复现的 bug、给已有函数补测试、解释一段调用关系、按明确规则修改多处相似代码。

有些任务也能做，但在开始前需要你先给出决定：

| 你说的话 | 缺少的决定 | 更好的开场 |
|---|---|---|
| “把页面做得更好看” | 面向谁、希望改善什么、哪些视觉不能动 | “保持现有品牌色，提高手机端表单可读性，先给出两个方案” |
| “优化性能” | 慢在哪里、当前数据、可接受的代价 | “列表首次打开约 2 秒，先找出耗时最大的步骤，不改数据一致性” |
| “重构登录模块” | 为什么重构、哪些对外行为必须保持 | “为了拆分测试困难的逻辑重构，接口和锁定规则保持不变” |

工具可以搜索代码，却不知道公司愿意承担多大风险；可以生成三个界面，却不知道哪个符合品牌；可以运行测试，却不知道没有测试覆盖的业务规则是否正确。这些不是模型能力够不够强的问题，而是任务本来就缺少人的选择。

反过来，也不要把文件搜索、重复修改、命令执行全留给自己，再只让 Claude Code 生成一小段代码。那样虽然“用了 Claude Code”，实际仍然停留在聊天窗口的用法。合理的分工是：你给目标和边界，它承担项目内的调查与执行，你根据可见结果做关键判断。

## 到这里，你已经走完了一次完整任务

回头看，整个过程并不神秘：

```text
进入正确项目
→ 说清现象和目标
→ 先调查相关文件
→ 确认方案后修改
→ 用 diff 和测试检查
```

Claude Code 的价值，不是替你说一句“这段代码应该这样写”，而是能在真实项目里把寻找、修改和验证连起来。你的职责也没有消失：业务目标由你定义，高风险动作由你决定，最终结果由你确认。

第一次练习时，宁可选择一个小而明确的 bug，也不要一上来就说“重构整个项目”。小任务能让你看清每一步发生了什么。等你熟悉这条工作线，再逐渐增加任务范围。

你可以马上换一个项目再练一次。选择下面任意一种小任务：

- 把一个表单里的模糊报错改成用户能理解的提示；
- 为一个已有函数补上缺失的边界测试；
- 找出某个页面按钮点击后经过了哪些函数；
- 修复一处可以稳定复现的样式错位。

练习时不要复制本章的登录需求。只沿用同一套节奏：先描述看得见的现象，让它调查真实文件，确认方向后再改，最后同时看差异与运行结果。如果中途它做出了你没要求的修改，立刻停下来问“这项修改与目标有什么关系”。能问出这句话，说明你已经开始掌握与编码 Agent 协作的关键，而不是被它的执行过程牵着走。

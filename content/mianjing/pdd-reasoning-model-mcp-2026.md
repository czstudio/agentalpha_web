## 1. 真题：为什么有些推理模型不支持 MCP 协议

**问法**：「为什么有些特定的推理模型不支持 MCP 协议？」

错误示范一：答「模型比较新，还没来得及适配，等厂商更新 SDK」。面试官指出这不是适配问题：MCP 底层靠 Function Calling 驱动，模型连 FC 都支持不了的话 MCP 无从谈起。

错误示范二：答「思维链太长占满上下文，没空间放工具定义」。面试官明确说上下文窗口不是核心矛盾。

答题要点，按机制推演：

1. **推理模型的机制**：给答案前先跑一段完整的思维链（thinking tokens），在思考里推演、验证、推翻重来。代表是 o1/o3、DeepSeek-R1、Claude 扩展思考。这段思考是**一次性连续生成的，不能中途打断**——断了推理上下文就接不上。
2. **工具调用的机制**：天然是多轮交互——模型输出调用请求、暂停、等外部执行、拿结果再继续。**中断和等待是内置需求**。
3. **冲突点**：一个不能停，一个必须停。思考链跑到一半暂停去等工具结果，前面的推理状态就废了；不停的话模型又拿不到工具返回的事实。
4. **业界的折中**：后来的方案（如 o3、Claude 扩展思考的工具集成）把工具调用放在思考阶段结束之后，保证思考过程一次性完整生成，需要外部信息就再开一轮。

**追问链**：「那 MCP 呢？」答：MCP 的工具调用最终落到 Function Calling 的输出格式上，推理模型 FC 支持不完整，MCP 这层自然用不起来——依赖链断了。

## 1. 真题：都能做工具调用，具体什么场景选哪个

**问法**：「Function Calling 和 MCP 都能做工具调用，具体什么场景下该选哪个？」

错误示范一：答「小项目用 Function Calling，大项目用 MCP」。面试官反问：大项目的工具只在内部用、不需要复用呢？规模只是一个因素。

错误示范二：答「工具少 FC、工具多 MCP」。面试官再补：如果社区已经有现成的 MCP Server，哪怕只要一个工具，你还自己手写对接吗？

答题要点，按判断维度展开：

1. **复用需求（核心判断）**：这个工具会不会在本应用之外被用到。不会，临时接一两个工具，Function Calling 直接写在代码里最快；会，跨项目跨团队复用，封装成 MCP Server 一次实现到处用。
2. **生态现成度**：GitHub、数据库、浏览器这类通用工具社区已有现成 MCP Server，配置几行就能接，比自己写对接代码划算。
3. **部署环境**：MCP 是独立进程，要考虑部署运维；本地场景 stdio 子进程简单，远程场景 Streamable HTTP 有服务化管理成本。
4. **系统形态**：做 Agent 系统（工具来源多、数量大）倾向 MCP 的统一注册和发现，手写 FC 的 schema 散在各处会越来越难管。

收尾补一句平衡：「两者不是二选一，核心私有工具内嵌 FC、通用能力接 MCP 的混用是常态。」

**追问链**：「MCP 的额外成本是什么？」答：独立进程的部署运维、连接管理、团队对协议的理解成本；工具少且不复用时这些成本收不回来。

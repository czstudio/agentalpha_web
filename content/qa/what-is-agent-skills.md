## 先这样答

Agent Skills 是一种组织知识的方式：把「怎么做某类任务」装进一个文件夹，里面有一份说明文档，描述这个技能做什么、什么时候用、步骤是什么，可以再附上脚本、模板和参考资料。Agent 平时只看到每个技能的名字和一句话简介，判断当前任务需要时，才把完整说明读进上下文，按里面的流程执行。

和提示词、MCP 的关系分开说。和提示词比：传统做法把所有流程都写进系统提示词，技能一多上下文就撑爆，而大部分会话每次只用到其中一两套流程。Skills 把这些内容从常驻改成按需加载，上下文里平时只放目录。和 MCP 比：MCP 解决工具接入，定义模型怎么发现和调用外部服务；Skills 装载的是流程和知识，告诉模型处理这类任务的步骤和注意事项。两者互补：可以用 MCP 接入数据库工具，再用一个 Skill 写清楚报表类任务先确认统计口径、再调哪个工具。

总结：Skills 解决的是「能力多了之后怎么组织」。点出「它改变的是知识的装载时机」，和「改变工具接入方式的 MCP」分开讲，这道题就答清楚了。

## 面试官会怎么追问

- **「Skill 里的脚本和直接注册工具有什么区别？」** 脚本打包在技能内部，模型读了说明才知道有它、怎么用，属于某个流程的附属；工具是平台级注册的，所有任务可见。流程内的固定操作适合做成脚本，跨任务的通用能力适合注册成工具。
- **「什么时候值得做成 Skill？」** 两个条件同时满足：流程有明确的步骤能写成文档，而且不是每次会话都需要。低频但复杂的任务（某类报告生成、发布流程）收益最大，高频简单任务写在提示词里更省事。
- **「Skill 会失效吗，怎么维护？」** 会。依赖的外部接口变了、流程改了而文档没改，模型就按过时流程执行。把每个技能当一个小东西维护：有版本、有更新记录，流程变更先改文档再改实现。

## 回答的坑

- 把 Skills 说成「新的工具协议」。它不定义调用接口，本质是文档和资源的组织加载方式，和 MCP 解决的是两个问题。
- 认为技能越多越好。每个技能都占目录里的一个位置，装载后的说明也占上下文，堆一堆低频技能反而稀释模型对关键流程的注意力。

## 先这样答

A2A（Agent2Agent）是 Google 在 2025 年牵头推出、后捐给 Linux 基金会的开放协议，解决多智能体之间的互操作问题：你的 Agent 和我写的 Agent 来自不同框架、不同厂商，怎么互相发现、互相了解对方能干什么、怎么把任务委托过去并跟踪进度。

它和 MCP 的分工可以这样记：MCP 是纵向的，Agent 往下接工具和数据，把能力接进来；A2A 是横向的，Agent 和平级协作，把任务委托出去。一个典型的系统里两者同时存在：你的主 Agent 通过 MCP 连数据库和内部 API，同时通过 A2A 把「机票比价」这个子任务委托给外部的差旅 Agent。

A2A 协议里的核心概念有三个。Agent Card：每个 A2A Agent 提供一张自描述的名片（JSON 文档），写清自己能做什么、地址在哪、怎么认证，对方靠它发现和了解你。Task：协作的基本单位，委托方创建任务、被委托方执行并回报状态，任务可以跑到几十秒甚至几天，支持中途查询进度。Agent Card 让「发现」标准化，Task 生命周期让「委托」可跟踪。

设计上 A2A 刻意保持不透明：被委托的 Agent 不暴露自己的内部思考过程和工具清单，只承诺输入输出。这是个重要的工程立场，保护了各家的实现细节，也意味着委托方要做结果验收而不是过程监控。

## 面试官会怎么追问

- **为什么不直接用 MCP 做 Agent 互联？** 把另一个 Agent 包装成 MCP 工具也能跑通短任务，但 Agent 协作有长时任务、进度跟踪、多轮澄清、能力协商这些需求，MCP 的工具调用模型覆盖不了。
- **A2A 现在落地情况怎么样？** 协议推出后主要厂商和框架响应较多，但在生产里大规模用起来的案例还少，现阶段重点是了解概念和设计立场，面试答到「互补、纵向横向」这个层次就够了。
- **委托方怎么验收结果？** 靠 Artifact（产出物）加明确的验收标准，重要任务委托方自己做结果校验，不能因为协议通了就默认结果可信。

## 回答的坑

- 把 A2A 和 MCP 讲成竞品。方向搞反（说成「A2A 取代 MCP」）是这道题最常见的翻车点。
- 过度展开协议细节。这道题考的是架构层面的分工理解，细节点到 Agent Card 和 Task 就停。

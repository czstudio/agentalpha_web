## 先这样答

我会把这个智能客服 Agent 设计成四层：意图路由、检索、工具调用和带引用的回答。先识别用户问题属于账户、播放、创作还是审核申诉，再选择处理路径。用户问账户状态时，Agent 调用查询工具。用户要提交审核申诉时，Agent 走申诉工具。路由只决定下一步做什么，不直接替用户断言处理结果。

检索层使用帮助文档和工单历史。帮助文档提供答复依据，工单历史补充相关问题的处理信息。生成层根据检索结果组织回复，并标出引用。这样，用户能看到回答依据。工具层处理需要实际查询或提交的问题。Agent 查到账户状态后，再回答个人账户问题；需要提交申诉时，再调用对应工具。

护栏放在回答和工具调用之前。遇到敏感话题，Agent 转人工处理。遇到高投诉风险操作，Agent 先向用户二次确认，再执行操作。评估时，我看解决率、转人工率和响应延迟。解决率看问题有没有解决，转人工率看人工接手的情况，响应延迟看用户等了多久。三项要一起看，不能为了减少转人工而让 Agent 处理本该转人工的问题。

## 面试官会怎么追问

- **「账户状态和帮助文档都能用，你怎么决定走哪条路径？」** 先按问题意图路由。用户问一般规则，就检索帮助文档和工单历史。用户问自己的账户状态，就调用查询工具，不把通用说明当成个人账户状态。
- **「审核申诉怎么处理，才不会让 Agent 擅自操作？」** 先识别审核申诉意图，再检索相关依据。需要提交申诉时才调用工具。若操作有高投诉风险，先让用户二次确认；遇到敏感话题则转人工。
- **「你怎么判断这个 Agent 做得好不好？」** 我看解决率、转人工率和响应延迟。解决率看问题是否解决，转人工率看人工接手情况，响应延迟看回复速度。不能只追求低转人工率，敏感话题仍要交给人工。

## 回答的坑

- 只讲 RAG，不讲账户查询和申诉提交，就没回答 Agent 怎么处理需要操作的问题。
- 只讲自动解决，不讲敏感话题转人工和高投诉风险操作二次确认，就漏了关键护栏。

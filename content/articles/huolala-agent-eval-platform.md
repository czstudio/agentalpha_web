我们团队最近把客服和调度业务的 Agent 搬进了生产环境。从 Demo 演示到稳定落地，我们踩过无数坑，最终搭建了一套公司级的 Agent 评测平台。这篇文章盘点我们是怎么把 Agent 质量从不可控变成可量化的。

## 一、为什么业务 Agent 评测这么难

### 1.1 一个让人尴尬的交付现场

我们花了一个月时间，用工作流和自研大模型做出了一个调度助手 Agent。Demo 演示时效果极好，意图识别精准，工具调用顺畅。

但一上线就暴露了问题：

* **回答漂移**：昨天按标准回答的费用问题，今天版本微调后直接给用户承诺了优惠券；
* **工具误调/死循环**：遇到复合查询时，Agent 反复调用同一个接口，直到 Token 耗尽超时；
* **非确定性输出**：测试环境 100% 通过的用例，线上遇到微小 Prompt 扰动就答非所问；
* **性能崩塌**：高并发下首字延迟从 800ms 飙到 5s 以上。

排查日志时最头疼的是，单步推理看着都合情合理，但最终结果就是错的。没有统一基准时，我们改一处 Prompt，往往修好一个 Bug 又引入三个新缺陷。

![神秘的程序员们：成功啦！但为啥呢？](/images/articles/huolala-agent-eval-platform/meme_mystery_programmer.png

*图 1 ｜ 网上真实漫画：改完代码运行成功，但说不清为什么（《神秘的程序员们》）*

### 1.2 核心症结：传统测试与单点打分的双重失效

传统测试和单点评估解决不了业务 Agent 的问题，因为我们遇到了三重失控：

![传统接口测试 vs 业务 Agent 评测](/images/articles/huolala-agent-eval-platform/fig1_three_losses.png

*图 2 ｜ 传统接口测试与业务 Agent 评测的差异（图片来源：货拉拉技术公众号原文）*

1. **确定性断言失效**：大模型的输出是概率性的，传统的 equals 或正则断言无法判断语义准确度、幻觉和业务红线。
2. **上下文与工具链路复杂**：业务 Agent 是多轮迭代的动态决策链路。从用户提出目标开始，要依次完成意图理解、计划生成、步骤选择、工具调用、结果处理，再根据中间结果修正规划。链路里集成了企业 MCP 工具库、知识库和工作流。错误会沿着「意图理解 - 参数提取 - 工具选择 - 结果组装 - 规划修正」逐级放大。
3. **性能度量维度跃迁**：性能指标不再只是 QPS，TTFT、TTLT、TPS 直接决定了用户体验。

![Agent 执行链路](/images/articles/huolala-agent-eval-platform/fig2_chain.png

*图 3 ｜ Agent 的多轮迭代执行链路（图片来源：货拉拉技术公众号原文）*

**Agent 能跑，不代表能用；单次回答漂亮，不代表生产稳定。** 生产级交付必须依靠完备、自动化和客观的评测基础设施。

## 二、评测范式演进：从「凭感觉点测」到「工业化流水线」

我们在建设评测体系时经历了三个阶段：

| 演进阶段 | 核心特征 | 评测手段 | 痛点与局限 |
| --- | --- | --- | --- |
| 第一代：人工盲测与单点 Prompt 打分 | 靠工程师人工单句提问，肉眼比对效果 | 少量 Excel 用例，单轮输入输出校验 | 覆盖度极低、主观性强、无法自动化回归 |
| 第二代：离线数据集与单一 LLM-as-a-Judge | 引入离线 Benchmark 数据集与大模型裁判打分 | 离线批处理脚本、单一相似度算法 | 裁判模型有幻觉与自评偏见、脱离发布流水线、缺性能度量 |
| 第三代：全生命周期自动化评测平台 | 业务规则 + 智能裁判 + 拦截隔离 + CI/CD 门禁 + 性能压测 + 线上巡检 | 多元协议打通、动态流水线卡点、多维基准度量 | Agent 质量可量化、可验证、可卡点、可持续迭代 |

六大支柱及解决的问题：

| 支柱 | 要解决的核心问题 | 平台的具体实现 |

| 支柱四：体系化评测计划与全景报告聚合 | 怎么管理多版本评测目标、横向对比并产出业务可读的全景报告 | 评测计划目标管理与版本基线对比；功能与性能一体化看板，深度集成发布系统；报告自动生成并推送飞书群，对接自研测试质量平台 |
| 支柱五：大模型性能与稳定性压测 | 怎么评估 Agent 在高并发与流式交互下的极限表现 | 自研 LLM 压测引擎；支持固定/阶梯/线性爬坡曲线；精确度量 TTFT、TTLT、RPS 及 Token 吞吐 |
| 支柱六：CI/CD 门禁、追踪与缺陷归因 | 怎么无缝嵌入交付流水线，做长会话还原与低分缺陷归因 | 支持准入（Admit）与准出（Exit）评测，分数不达标自动熔断发布；低分专项筛选与专家人工复核 |

## 四、核心支柱的工程落地与技术细节

### 4.1 支柱一：全方位智能体资产治理与链路拓扑

![评测实验室结构](/images/articles/huolala-agent-eval-platform/fig4_pillar1.png

*图 5 ｜ AgentNameSpace 评测实验室与智能体注册结构（图片来源：货拉拉技术公众号原文）*

不同业务线对 Agent 的要求不同。我们通过评测实验室进行多租户隔离，并建立统一的 Agent 元数据模型：

* **命名空间与项目隔离**：按项目空间和业务线做多租户资源隔离；
* **多平台纳管**：对接内部自研工作流/模型平台及自定义 Agent HTTP 服务；
* **版本与环境追踪**：关联代码版本、Prompt 版本、知识库切片和运行环境（PRE/PRD），保证每次评测可复现；
* **流式交互与协议解析**：原生支持非流式与 SSE 流式响应，用 resultPath（JSONPath）与 resultType（Path / Shell）对多模态异构结果做精准提取。

参数动态映射与拦截器上，我们设计了三类切点拦截器：

* **三级切入点**：TASK_BEFORE、SESSION_BEFORE、REQUEST_BEFORE；
* **切点类型与变量注入**：支持 AGENT_CASE（用例数据集动态注入）与 SHELL_REF（脚本动态引用），把计算产物强类型映射成 String、Number、Boolean、JSONObject 或 JSONArray，注入 Agent 请求报文。

针对 Agent 输出的非标准嵌套 JSON、Markdown 混杂或特殊格式，我们提供了 AgentConfig 规则引擎：

* **嵌套 JSON 快速点选**：页面调试时支持点选提取 response 字段与通用字段映射；
* **内置 Groovy 脚本执行**：支持在沙箱里动态运行清洗逻辑，把复杂输出结构化成标准评测载荷。

调用链拓扑与标签体系上：定义源 Agent 与下游目标 Agent 的调用关系，支持 ANY / ALL 复合匹配规则；在智能体维度建立「业务域、能力项、风险等级、用例类别」多维标签，按标签动态下发用例集与调用链路由。

### 4.2 支柱二：数据集测试数据合规校验与准入门禁

垃圾数据输入只会产生垃圾评测结果。测试数据集未校验就下发，会出两类问题：

1. **数据污染与环境越界**：误用线上未脱敏的生产数据或非测试环境标识，Agent 调用工具时触发非预期的真实写操作；
2. **算力与 Token 浪费**：用例格式错误导致 Agent 跑几十轮对话后崩溃，白白消耗大量推理 Token。

为此我们构建了基于测试数据校验规则引擎的前置准入卡点：

![数据准入校验流程](/images/articles/huolala-agent-eval-platform/fig5_datacheck.png

*图 6 ｜ 前置数据准入校验引擎流程（图片来源：货拉拉技术公众号原文）*

* **多维动态数据校验规则引擎**：按需沉淀细粒度的测试数据契约规则。强制校验请求参数里是否包含合法的测试环境标识，严禁未脱敏的线上真实数据或非测试账号混入；深度检查 Headers、Params、Body 是否符合目标 Agent 入参 Schema，包括必填字段、类型、枚举范围和 JSON 合法性。
* **发起前批量预检与秒级阻断**：在触发流水线准入/准出或用户点击发起评测时，系统调用 checkAgentInfoAndCases 对所选数据集做全量扫描。发现 1 条用例不合规即阻断评测调度，不生成评测 Job；同时返回校验诊断报告，指明具体用例和违规字段，引导维护者在前端修正。

### 4.3 支柱三：多模复合智能裁判与多维评分体系

单一的大模型裁判存在打分漂移、缺乏分层业务约束和多轮对话孤立评判的问题。对订单号、金额、JSON 数据结构等强确定性事实，只靠 LLM 容易漏检误判。

我们的做法是「内置五大确定性规则 + 三维 Prompt 组合裁判 + 裁判引擎抗波动 + Session 级红线穿透」：

![多模复合裁判体系](/images/articles/huolala-agent-eval-platform/fig6_judge.png

*图 7 ｜ 多模复合智能裁判体系（图片来源：货拉拉技术公众号原文）*

**五大内置确定性规则引擎（硬约束打分）**由计算型引擎直接执行，毫秒级且零幻觉：

* **结构化校验**：校验输出 JSON / XML 的格式合法性、字段完整性、Key-Value 数据类型及嵌套 Schema 契约；
* **正则匹配**：用预置或自定义正则校验订单号、手机号、车牌号、金额、日期等关键业务实体的提取准确率；
* **硬匹配**：对标准枚举值、固定系统指令、特定操作返回码做字面全等判定；
* **关键词匹配**：支持「必须包含词」「禁止违规词」和命中词频阈值，用于服务禁言、红线合规与话术覆盖度校验；
* **语义相似度**：基于文本嵌入向量计算回答与标准参考答案（Golden Reference）的余弦相似度。

**三维 Prompt 模板动态组合体系**，分层注入：

* **平台级模板**：沉淀全局通用评测元规则，包括 0~100 分制尺度、事实性与幻觉判定准则、扣分点输出格式；
* **Agent 维度模板**：注入具体业务 Agent 的角色定位、业务边界与专业规范；
* **用例维度模板**：绑定单条用例的特定上下文、意图判定要点（Rubric）、期望提取参数和特定判定逻辑。

**裁判引擎抗波动机制**：

* **并发多次采样**：对单条评测产出并发下发多路独立裁判请求；
* **离群过滤与均值聚合**：剔除偏离度过大的极值，对有效置信区间内的打分做加权均值聚合；
* **方差监控与置信度熔断**：多次采样方差超过阈值时，自动推入人工复核池。

**Session 级多轮综合评分：短板与红线穿透原则**。孤立地对每一轮打分再平均会掩盖关键阶段的崩溃。我们在会话级度量里引入端到端综合评分：

* **红线与短板穿透**：任意一轮触发超级红线违规或核心步骤严重错误，该单项扣分直接穿透到全局总分；
* **渐进加权平均分**：多轮对话越长，上下文腐烂概率越高，系统采用前轻后重的渐进权重曲线，越靠后的轮次权重越高。

**客观评测与主观评测并行：人工校准 + 自动沉淀**：

![客观评测与主观评测对比](/images/articles/huolala-agent-eval-platform/fig7_triple.png

*图 8 ｜ 客观评测与主观评测的定位与分工（图片来源：货拉拉技术公众号原文）*

* **客观评测**覆盖高频、结构化部分，由确定性规则引擎执行，守住质量底线；
* **主观评测**覆盖开放性、高价值场景，由多模复合智能裁判执行，拉升体验上限；
* **人工复核校准 + 自动沉淀**：争议用例、红线触发样本或重点版本，由业务专家在可视化复核工作台人工打分；修正后的样本自动沉淀为黄金对齐数据集，反哺迭代裁判 Prompt 与评分规则。

### 4.4 支柱四：体系化评测计划与全景报告聚合

把评测能力嵌进 CI/CD 流水线是拦住带缺陷上线的核心防线：

![评测计划与报告聚合](/images/articles/huolala-agent-eval-platform/fig8_report.png

*图 9 ｜ 评测计划与报告聚合流程（图片来源：货拉拉技术公众号原文）*

* **评测计划与版本对比基线**：支持针对不同业务能力项设定目标分与权重，自动计算加权达标情况；显式关联当前版本与对比基线版本，直观度量迭代前后的分数波动。
* **功能 + 性能 + 安全一体化全景报告**：把智能体元数据、响应配置、功能评测明细、性能压测数据与安全表现整合成一站式评测画像；评测结束自动生成报告并推送到指定飞书群组。

### 4.5 支柱五：大模型性能与稳定性压测引擎

针对业务大模型在长文本、流式输出、高并发场景下的性能瓶颈，我们内置了自研 LLM 性能压测引擎：

![LLM 压测引擎](/images/articles/huolala-agent-eval-platform/fig9_pressure.png

*图 10 ｜ LLM 异步压测引擎（图片来源：货拉拉技术公众号原文）*

* **多元压力曲线**：支持固定并发、线性爬坡，模拟早晚高峰流量；
* **流式精准计时**：针对 SSE 流式响应，精确捕捉首 Token 到达时间（TTFT）与完整文本生成时间（TTLT）；
* **压测指标大盘**：监控响应耗时（RT）、首字延迟（TTFT）、吞吐量（RPS）、完整耗时（TTLT）和请求失败率。

### 4.6 支柱六：CI/CD 门禁、追踪与缺陷归因

评测要落到交付流程里才起作用。我们通过嵌入流水线、提供排查工作台来保障长期运行质量：

![CI/CD 门禁流程](/images/articles/huolala-agent-eval-platform/fig10_cicd.png

*图 11 ｜ 准入/准出门禁与低分缺陷处理流程（图片来源：货拉拉技术公众号原文）*

* **CI/CD 流水线准入准出门禁**：准入评测在合并代码或变更 Prompt 时自动触发核心冒烟用例集；准出评测在发布前执行全量基准测试，分数不达标流水线直接返回 FAIL 并阻断发布。
* **低分专项筛选与缺陷处理**：低分雷达支持按分数阈值快速拉取低分用例列表；专家可在工作台对争议结果二次复核与改分，修正样本沉淀为优化数据；线上分钟级自动巡检生产环境，发现异常即时告警。

| --- | --- | --- | --- |

### 5.2 缺陷拦截：从「上线救火」到「前置防线」

平台前置拦截的缺陷覆盖智能体执行过程的六类问题：

| 问题大类 | 典型场景 | 占比 |
| --- | --- | --- |
| 意图与指令理解 | 意图识别错误、指令忽略/漂移、语义理解偏差 | 33.84% |
| 智能体与工具执行 | 工具调用幻觉、执行死循环、状态记忆不同步 | 31.12% |
| 回答准确性 | 事实性幻觉、检索漏召回、逻辑推理断层 | 25.38% |
| 性能与响应体验 | 首 Token 超时、全量超时、输出抖动 | 5.44% |
| 格式与输出规范 | 格式规约破坏、生成重复死循环、流式解析报错 | 2.72% |
| 安全合规 | 提示词注入/越狱、敏感信息泄露、过度拒答 | 0.91% |
| 其他 | 误操作、重复提交 | 0.59% |

核心结论：意图理解与工具执行两类问题合计约 65%，是 Agent 质量问题的大头——这正是传统单点打分式评测最容易漏掉的部分，因为传统评测只看最终答案对不对，不关心中间链路是否正确。

### 5.3 业务实战：AI 邀约的效能变化

以 AI 邀约业务为例，接入评测平台后在需求吞吐量翻倍（+80%）的背景下，线上质量与研发效能同步改善：

| 核心指标 | 灰度前 | 灰度后 | 变化 |
| --- | --- | --- | --- |
| 月均需求吞吐 | 2.2 个 | 4.0 个 | 需求量 +80%，支撑业务迭代节奏加快 |
| 月均发布次数 | 33 次 | 14 次 | 单次发布质量提升，发布次数下降 57% |
| 月均质检 Badcase | 439 个 | 351 个 | 上线质量提升，线上体验改善（减少 20%） |
| 算法投入人力 | - | 释放 41.5 人天/月 | 降本提效 |

在交付效率提速、线上质量守住的条件下，业务指标没有因为加评测而下降。质量平台的价值不是拖慢迭代，而是让快速迭代时质量有保障。

### 5.4 全场景覆盖：从高频回归到深度探隐患

平台已打通自研工作流平台、大模型、自定义 Agent 协议等多元异构入口，以功能、性能、安全及自动化流水线等多维评测能力，覆盖公司不同类型的智能体场景。从使用模式看有两类典型范式：

* **高频防退化型**：迭代频繁、回归量大，平台承担高强度自动回归，确保核心主流程稳定不退化；
* **深度探隐患型**：场景复杂、工具链深，平台靠丰富的场景用例和多模裁判能力，挖掘复杂工具调用里的隐蔽异常。

头部 3 个重点项目贡献了近 85% 的评测量，拦截了 60% 的核心质量缺陷——平台既能扛住海量高频回归的吞吐压力，也具备针对复杂 Agent 的深度探测能力。

## 六、未来演进

业务 Agent 评测还在快速演进，我们接下来打算往这三个方向走：

1. **从「静态用例」走向「Agent 对抗评测（Agent-vs-Agent Evals）」**：借鉴对抗生成思想，由专门的红队进攻 Agent 动态生成刁钻的边缘用例与多轮对话陷阱，持续对业务 Agent 做自动化压力对抗。
2. **多 Agent 协同系统（Multi-Agent System）链路评测**：当业务架构从单 Agent 变成协调者加多个专业子 Agent，评测重点从单体输出质量扩展到 Agent 间通信效率、协作死锁检测、任务分解合理性及全局状态一致性。
3. **评测驱动的自适应优化（Eval-Driven Auto-Tuning）**：把评测结果直接接到 Prompt 自动调优器与模型微调数据飞轮上，评测分数低于阈值时自动提炼失败样本并优化 Prompt，实现自我迭代。

## 结语

对业务 Agent 的生产交付来说，评测不是上线前的一道手续，而是一套持续运行的工程系统。我们最后沉淀下来的分工是：确定性规则处理硬事实，智能裁判处理开放语义，数据校验拦住脏输入，门禁熔断卡住发布，压测与巡检盯着线上。每一环都有明确的执行位置和判断标准，Agent 质量因此从凭感觉变成看数据。

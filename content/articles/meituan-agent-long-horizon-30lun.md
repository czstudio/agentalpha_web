一个任务算不算长程，看的不是它跑了多久，而是步骤之间是否相互依赖结构。长程里最难防的错误，是单步全对、前提已错，这类错误叫级联错误。

**👔 面试官：**你负责的 Agent 跑一个数据分析任务，三十多轮工具调用，最后交付的结论是错的。你翻日志，发现中间每一步的输出单看都说得通。你怎么定位是从哪一步开始错的？

**🙋‍♂️ 我：**找最早出现异常的那一步，看它和前面哪一步对不上。

**👔 面试官：**它每一步都基于自己上一步的状态往下算，算得没错。错的是更早生成、后来一直被沿用的那个中间结果。

**🙋‍♂️ 我：**那我把每一步的状态快照都存下来，回头做二分定位。

**👔 面试官：**存快照帮你查，帮不了你防。再问你一个更实际的：你怎么知道它「交付完成」了？

**🙋‍♂️ 我：**它自己说完成了……

**👔 面试官：**对，它说完成了。如果它只处理了三分之二的文件、另外三分之一跳过了，它会主动告诉你吗？

**🙋‍♂️ 我：**大概率不会，它甚至会报一个漂亮的完成率……

这段对话从「怎么排查」开始，落到「怎么信任」。面试官问的其实是长程任务的三层：一个任务算不算长程、错误在长程里怎么累积、任务状态应该放在哪里。下面逐层拆。

### 💡 简要回答

**第一层，先分清判据。**决定一个任务是不是长程任务的，不是运行时长，而是步骤之间的依赖结构：前一步的输出是不是后一步的必要输入、错了能不能就地纠正、状态要不要跨窗口重建。跑一整夜的独立批处理不算长程，只是运行时间长；十几分钟内改五个文件、且改动之间要保持兼容，反而算长程任务 \[1\]。依赖链一长，错误就有了累积的通道。

**第二层，错误的累积机制。**浙大与蚂蚁的知识图谱联合实验室测过一个数：多轮数据分析任务按进度从前 10% 到后 10% 对齐，正确率下降接近 47 个百分点（项目页读数 46.8）\[2\]。他们对 3207 个错误轮次做归因，上下文记忆、状态管理、级联三类长程错误合计占 52% 到 69%，其中级联错误占比最大：当前轮的计算完全正确，错的是更早生成、又被沿用的中间状态 \[2\]。这类错误不报错，后面每一步都在错误的前提上继续推进。所以「单步都对」和「结果对」是两件事。

**第三层，状态必须搬出上下文。**把任务状态寄托在不断膨胀、又被反复压缩的单条上下文里，是上面那类错误的来源。工程对策分三层落地：把任务状态外置成结构化文件或状态树，让每一步的进度、口径、已确认事实可读可写可回退；让审计独立于执行，由不接触原始推理过程的模块核对「做完了没有」；压缩上下文时保留恢复通道，压掉的东西必须找得回来。

一句话：**判据看依赖结构，级联错误靠状态外置来断，能不能交付靠独立审计来判。**

### 📝 详细解析

判据：决定长程的是依赖结构，不是运行时长

先把这个词说准。《Towards Long-Horizon Agents》这篇综述给了一个统一的形式化定义：`Agent = π_θ ⊕ H`，也就是基座策略（模型权重里的能力）与运行时 Harness（循环、记忆、工具、编排、验证等外部支架）耦合成的系统 \[1\]。它想说明的是，长程能力不是基座模型的单独属性，而是策略与支架耦合出来的结果。

综述按「执行要跨出单个上下文多远」把长程分成三级，且三级嵌套 \[1\]：

| 
级别

 | 

跨度

 | 

新增的要求

 |
| --- | --- | --- |
| 

H1 上下文内

 | 

单窗口，约分钟级

 | 

交互式推理要在窗口内完成

 |
| 

H2 跨上下文

 | 

跨窗口、跨会话，约小时到天

 | 

状态与记忆要能跨窗口存活

 |
| 

H3 跨任务流

 | 

开放式任务流

 |

 |

这个分级解释了为什么「把上下文窗口做大」不构成完整答案：窗口扩大只抬高 H1 的天花板，H2 和 H3 需要的跨窗口存活与经验积累，窗口本身不提供。

![](/images/articles/meituan-agent-long-horizon-30lun/fig02.jpg)

— 三级跨度：窗口做大只抬高 H1 的天花板

决定长程的是依赖结构，不是运行时长。

顺着这个分级看招聘要求就很容易对上。字节把「长程任务规划」和「上下文与状态管理、工具调用、执行控制、记忆、沙箱」写在同一段里 \[14\]；美团的表述是「规划、决策、工具使用与长时程任务执行能力」\[15\]；蚂蚁直接要求「长程任务、上下文管理、工具和知识集成」\[16\]；腾讯把「Durable Execution 长任务执行框架」列进 Agent 基础设施 \[17\]；阿里云写的是「长链路任务的可靠性保障：任务断点续传、局部重试、人机协同介入点设计」\[18\]。这几条指向同一件事：面试考的不是模型能不能规划，而是你有没有为「跑很久」准备一套状态与恢复的机制。

错误为什么累积：三类长程错误里级联占比最大

LongDS-Bench 那篇论文做了一件很有用的事：把长程失败按类型归因。3207 个错误轮次里，上下文记忆、状态管理、级联三类合计占 52% 到 69%（口径随基座模型变化），级联是其中最大的一类 \[2\]。

级联错误的形态值得单独记住：当前轮算得完全正确，错的是更早生成、被它当作前提沿用的中间状态。代码运行成功，用的却是错误版本的数据；统计口径在第五轮改过一次，第七轮还在按旧口径聚合。这类错误不抛异常，不产生任何可观测的失败信号，只会在最后交付时表现为结论莫名其妙。

![](/images/articles/meituan-agent-long-horizon-30lun/fig03.png)

图：LongDS-Bench 错误归因（纵轴为各错误类型占比，级联是最大一类）

论文还顺带测了依赖结构：每一轮平均直接依赖约 2.85 个历史轮次，最远的依赖平均往回追溯约 11.29 轮 \[2\]。这两个数字解释了为什么「看最近几轮」这种排查方式不管用：错误源头常常在十几个轮次之外。

「单步都对」和「结果对」是两件事。

排查本身也是一道独立的难题。中科院计算所与清华的工作构建了 1140 条非注入的真实失败轨迹（中位 145 步），结果显示最强的基线模型能精确定位到根因步骤的只有 13.2%，他们提出的方法做到 24.1% \[4\]。另一份来自微软等机构的工作收集了 2518 条真实轨迹、把 6967 个错误归成 78 类，发现六个前沿模型作为判官，正确指认「第一个错误」的比例不足三分之一，而一个自训的 4B 校验器反而超过它们 \[5\]。两组结果放在一起，指向一个很实际的结论：根因定位要靠结构化的状态记录，不要指望肉眼翻日志或者让一个强模型读一遍。

单步都对还会错：状态活在被反复压缩的上下文里

如果任务状态只存在于对话上下文里，它会经历三种损耗。

第一，上下文本身会随时间退化。上下文越长，模型对中间段落的召回越不可靠。有工作测算过，对话式 Agent 的 token 成本在朴素累积下随长度呈二次增长，因为每一轮都要重发全部历史 \[8\]。

第二，压缩会丢失可恢复性。压缩本身有价值：TokenPilot 用稳定前缀命中 KV Cache、对 HTML 与终端日志做确定性压缩，单个任务最多移除约 11.5 万字符的 HTML、88.3 万字符的日志，在 PinchBench 与 Claw-Eval 的隔离模式下把推理成本降低约 61% 与 56%，任务分数基本持平 \[9\]。但它的消融实验给出了边界：去掉恢复工具后成本回升，任务分从 80.92 掉到 77.12 \[9\]。压缩可以做，前提是压掉的东西找得回来。

![](/images/articles/meituan-agent-long-horizon-30lun/fig04.jpg)

— 单步都对，前提错了

压缩可以做，前提是压掉的东西找得回来。

第三，能力边界不等于可靠性边界。METR 持续测量前沿 Agent 的「时间视界」，即 50% 成功率对应的任务时长。截至 2026 年 5 月 8 日，Claude Opus 4.6 的 50% 视界约 718.81 分钟（接近 12 小时），同一批测量里 80% 视界只有约 69.87 分钟，相差约 10.3 倍 \[6\]。翻倍周期为 196.5 天，只看 2023 年之后的方法序列则缩短至 130.8 天 \[6\]。

这里要补一个容易忽略的细节：METR 明确指出 50% 与 80% 两个口径不是相互独立的估计，两参数 logistic 无法分别拟合曲线上下两端，因此改进 20% 口径的表现可能反而拉低 80% 口径 \[6\]。它的页面顶部还挂着「超过 16 小时的测量不可靠」的提示 \[6\]。正确的读法是：时间视界衡量的是能力边界，不能直接当作生产可靠性。面试里如果只报 50% 视界的数字，多半会被追问一句「那 80% 是多少」。

时间视界衡量的是能力边界，不能直接当作生产可靠性。

三道防线：状态外化、独立审计、可恢复的压缩

**防线一，把任务状态从上下文里搬出去。**MAGE 的思路是把记忆当执行状态管理，而不是当语义检索库：用一棵层级状态树承载任务进度，配四个算子（展开子任务、压缩已完成枝节、维护当前状态、修正错误状态），并支持回退到某个边界、在新分支上继续执行 \[7\]。它在 MemoryArena 上把成功率提高 7.8 到 20.4 个百分点，token 消耗降低 55.1% \[7\]。LongHorizon-Harness 走的是同一条路：把任务状态外置，结构定成「管理／执行／审计」三段，Terminal-Bench 2.1 上从 69.7% 提到 77.2%，WeaveBench 从 51.8% 提到 80.7% \[10\]。

**防线二，让审计独立于执行。**PILOT 批评了事后反思这类做法：更新发生在相关执行结束之后，提炼出的经验帮不到产生它的那次运行；而单 Agent 的自我修正，等于让执行者和诊断者争抢同一个上下文 \[13\]。它的做法是冻结模型参数，改成 supervisor-worker 架构：worker 在隔离上下文里执行，supervisor 通过双向通道对正在运行的 worker 发「转向」或「中止」，并把运行中发现的成功做法与失败模式写进技能库 \[13\]。实验收益里有个细节值得注意：实时转向在困难任务上的贡献明显（某配置下 19.7% 的成功运行受其帮助），在简单任务上是 0% \[13\]。独立监督的价值集中在难度高的那一段。

![](/images/articles/meituan-agent-long-horizon-30lun/fig05.jpg)

— 三道防线：外置、审计、可恢复的压缩

**防线三，先定义「完成」再谈交付。**阿里云把「人机协同介入点设计」和断点续传写在同一句里 \[18\]：可验证的完成条件、幂等可重试的动作、可回滚的检查点，三样齐了才敢让 Agent 长时间无人值守。验收标准说不清的时候（比如「做一份 PPT」），Agent 只能自己定义完成，而它定义的完成和你要的常常不是一回事。

能不能交付，靠独立审计来判。

训练侧与评测标尺：信用分配怎么给，长程能力怎么量

前面三条是外部支架的功夫，训练侧解决的是另一个问题：长轨迹的奖励太稀疏。

腾讯的工作 T1 用一个具体场景说明这件事：一道终端任务跑几十轮提交，最后只差一项测试没过，如果奖励只看「全成功」，整段轨迹里的有效工作全部归零。它的做法是把通过数变成稠密奖励，用 r = P / S，其中 S 取 20，取自通过断言数分布的第 90 百分位 \[11\]。奖励在轨迹片段末尾发放，再由价值网络向前分配 \[11\]。同一框架下，底座从 43.8% 经监督微调到 49.4%，强化学习后到 64.0%，强化学习贡献了后训练增益的约 72.3% \[11\]。

T1 论文自己标了三条边界，读数字时不能忽略：跨框架的分数不能直接比（同代最强模型在 Terminus-2 框架下 63.8%，换到另一个框架是 70.1%，而 64.0% 与 63.8% 只差 0.2 个百分点，论文承认这不足以构成稳定优势）；增益集中在中等难度，困难组只比监督微调多约 3 个百分点；长程专项基准上报的是部分完成程度分（27.9），不是完全解决率 \[11\]。另有一条路径是 turn 级信用分配：TRACE 用冻结参考模型的答案对数概率做时序差分估计，不需要 critic 也不需要过程标注，在 BrowseComp-Plus 上把 Qwen3-4B 从 7.2 拉到 35.6、Qwen3-30B-A3B 从 8.4 拉到 42.6 \[12\]。

![](/images/articles/meituan-agent-long-horizon-30lun/fig06.jpg)

— 稠密奖励与评测口径

评测侧的进展更能说明「长程」的难度。OSWorld 2.0 把任务换成 108 个真实工作流，人类完成一个任务的中位时长是 1.6 小时（上一代基准约 2 分钟），满思考配置下平均发起约 318 次工具调用（上一代约 30 次）\[3\]。在 500 步预算下，最强的模型也只有 20.6% 的任务全部完成，54.8% 拿到部分分 \[3\]。论文总结的失败模式是四种：丢掉约束、漏掉中途出现的信息、靠猜而不追问、跳过验证 \[3\]。

LongDS-Bench 的榜单同样要看口径：Lite 版（24 个任务、777 轮）上头部模型在 78 分附近 \[2\]；论文原版用 DSGym 评测，最高分是 48.45 \[2\]。两套分数不能串读。榜单是长程能力最诚实的一把尺子：没有长程评测，就没有可比较的进展。

两套分数不能串读。

面试官可能追问的三个问题

**「什么任务不该交给长程 Agent？」**三条排除判据：路径完全可预知的，写成工作流或脚本；单次调用就够的，不要套循环；目标本身说不清的，先别开工。LongDS 的归因里还有个反直觉发现：交互步数更多并不总意味着正确率更高，沿着错误状态多推理，只是把错误算得更细 \[2\]。

**「上下文窗口一直在变大，这套东西还需要吗？」**需要，但适用面会移动。窗口扩大解决 H1；H2 要状态跨窗口存活，H3 要经验沉淀，这两件事窗口本身给不了 \[1\]。综述提出的关系是协同演化：先由 Harness 实现的机制被内化进策略，更强的策略再解锁更高级的 Harness \[1\]。

**「如果只能改一处，你改什么？」**把任务状态从上下文里搬到一个可读可写的外部结构，并让它带上版本与来源。这一处改动同时解决三个问题：级联错误有了断点、根因定位有了依据、断点续跑有了载体。

SUMMARY

### 🎯 面试总结

回到开头那道题。面试官要的不是长程任务的定义，而是你有没有想过：一个任务跑久了之后，它凭什么还知道自己做到哪儿了。

这道题分三层答。第一层把判据说准，长程取决于依赖结构而不是时长，综述的 H1/H2/H3 分级可以直接用。第二层把错误机制说清，级联错误占比最大，形态是「单步都对、前提错了」，根因普遍在十几个轮次之外，前沿模型精确定位根因步的比例只有 13.2%。第三层把对策讲具体，状态外置（MAGE 的状态树与四个算子、LongHorizon-Harness 的管理／执行／审计）、独立审计（PILOT 的 supervisor-worker 与实时转向）、可恢复的压缩（TokenPilot：去掉恢复工具，任务分从 80.92 掉到 77.12）。

三个常见误区：把「跑得久」当成长程；把 50% 时间视界当生产可靠性（同一批测量里 80% 视界只有约 70 分钟，且 METR 明确说两个口径不独立）；只讲模型能力不讲状态与验收设计。

把**依赖结构、级联错误、状态外置**这三件事讲清楚，再补上训练侧的信用分配与长程评测口径，这道题就稳了。

阶段 9｜Agentic RL（1–1.5 周）

**学什么：**把「搜索/工具调用」建模成 RL 环境中的动作；交错推理加多轮搜索的训练流程；奖励函数设计与 PPO、GRPO、Reinforce 的选型对比；训练稳定性技巧；veRL、EasyR1、Search-R1 三个框架的技术路线与递进关系。

**动手做什么：**复现 Search-R1，训练一个 3B 到 7B 的小模型，让它在「思考、触发搜索、整合、回答」的结构里学会何时发起搜索。

**怎么验收：**报告必须包含训练前后模型检索次数与搜索触发位置分布的变化、答案质量与「引用有效率」的提升，以及 1 到 2 个失败样本的归因，比如长程任务跑到几十轮、单步都对结果却错时，如何判断该把状态外置成状态树、还是引入独立审计模块。

学员案例：字节 Seed、腾讯、京东 TGT、蚂蚁 PLAN-A、华为天才少年等录用结果；ICLR、KDD、ICML、NeurIPS、EMNLP、AAAI 等论文录用；USC、杜克、港科大等博士录取。

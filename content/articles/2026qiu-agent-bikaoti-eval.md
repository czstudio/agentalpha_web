QUICK ANSWER

### 💡 简要回答

评测正在成为 Agent 岗的区分度题。一位工程师今年 5 月分享了自己 20 轮 Agent 岗面试的完整记录，考点被收拢成四层：Agent Loop 模式、Skill 范式、Framework 底层、评测体系。关于评测这一层，他的原话是「Agent 是评测驱动的」「这个问题一定会被问到」。淘天 Agent 岗二面的 13 问里，也有一道「如何评估 RAG 系统的效果」的真题。招聘平台的岗位更能对上号：字节、美团、快手都有评测方向的独立岗位，实习和留用实习专门有名额。

评测有三个容易栽进去的坑。第一个是评分器本身出错，Anthropic 的 Opus 4.5 在 CORE-Bench 上最初只有 42%，修好评分脚本、换上限制更少的 scaffold 之后跳到 95%；第二个是口径选错，pass@k 和 pass^k 在单次成功率 75% 时，跑 3 次全成功的概率只有约 42%，k 越大两个指标讲的故事越相反；第三个是离线好不等于线上好，评估的对象是 harness 和模型的整体，还要面对分布漂移。

准备也有章法。学生校招给项目补评估数字：固定评测集、定两个指标、跑基线、改一处留对照、挑失败案例写归因。在职社招把验收讲成体系：自动化评测、生产监控、人工审查各拦什么、漏什么、怎么组合。再套一个四步答题框架：先定好坏、分层评测、离线加在线、主动讲失败。

DEEP DIVE

### 📝 详细解析

评测成了必考题

先看一份一手总结。今年 5 月，一位腾讯工程师在小红书分享了自己面 Agent 岗的完整记录：面了豆包、千问、阶跃、Kimi 和一些初创公司，一共 20 轮。他把考点收拢成四层：Agent Loop 模式、Skill 范式、Framework 底层、评测体系。

关于第四层，他的原话是「Agent 是评测驱动的」「这个问题一定会被问到」。具体考五件事：指标有哪些、离线和在线的评测流程分别怎么做、不同场景用什么评测框架、单轮和多轮任务分别怎么评、新特性或新模型上线时评测方案怎么定。

真题也有。牛客上一份淘天 Agent 岗二面面经，一共 13 问，其中一道是「如何评估 RAG 系统的效果？有哪些评估指标？」。二面还考评测，说明它已经是区分度题，不是开场送分题。

![](/images/articles/2026qiu-agent-bikaoti-eval/fig02.jpg)

— 四层考点里，评测体系是唯一标着「一定会被问到」的一层

招聘平台的岗位能对上这个判断。字节在招「豆包 AI 大模型评测算法工程师」（火山方舟），岗位职责里写着基于真实业务场景构建端到端评测 Pipeline，含 Agent 工具调用、RAG 检索、多轮对话等复合链路；美团实习岗的职责里明确列出大模型评测：构建自动化评测体系，设计 skills 评估方案；快手校招在招「大模型评测工程师（留用实习）」和「多模态评测算法工程师」。评测在这些公司是独立岗位，实习和留用实习有专门名额。

源头那边也有动静。Anthropic 在 2026 年 1 月的工程博客上发了《Demystifying evals for AI agents》，把评测的对象、指标口径、常见坑写成了一套方法论。一家头部模型公司专门为评测写长文，说明头部团队已经把它当成正经的工程问题。

「把评测当成搭完框架后的收尾动作，是把问题看小了。在头部团队那里，它已经是一门独立的工程学科。」

坑一：评分器本身出错

很多人对评测的印象是「写个脚本算个准确率」，觉得没什么技术含量。实际上第一个坑就在评分器里。Anthropic 自己吃过这个亏：Opus 4.5 在 CORE-Bench 上一开始只拿了 42%，排查后发现问题出在评分脚本。正确答案要求写 96.124991…，模型输出 96.12 就被判错；有些任务规格写得含糊，有些任务本身带随机性。修好评分脚本、换上限制更少的 scaffold 之后，分数跳到了 95%。

这段经历被写进博客，结论是「先审查评分器，再怀疑模型」。评分脚本也是工程代码，而且是整个系统里最容易静默出错的一段。

「先审查评分器，再怀疑模型。评分脚本是工程代码，也是最容易静默出错的一段。」

坑二：口径选错，结论跟着错

还是那篇博客，给了一组算术：一个 Agent 单次成功率 75%，跑 3 次任务，全部成功的概率是 0.75³，约等于 42%。这里有两个长得几乎一样的指标：pass@k 量的是 k 次里至少成功一次的概率，pass^k 量的是 k 次全部成功的概率。k 等于 1 时两者相等，k 等于 10 时，两个指标讲的是相反的故事。

![](/images/articles/2026qiu-agent-bikaoti-eval/fig06.jpg)

— 左 pass@k 至少一次成功，右 pass^k 全部成功，0.75³≈42%

Anthropic 给的用法是「一次性使用、成功一次就够的工具看 pass@k，要稳定执行任务的 Agent 看 pass^k」，因为面向真实用户的产品，用户期望的是每一次都可靠。面试里能主动讲出这组口径差异的候选人很少。讲得出来的，基本都真跑过评估，这个坑只有踩过才记得住。

「口径选错，结论跟着错。能把 pass@k 和 pass^k 讲清楚的人，大概率真跑过评估。」

坑三：离线好不等于线上好

Anthropic 在博客里给了一个容易被忽略的定义：当我们说评估「一个 Agent」时，评估的是 harness 和模型协作的整体。同一个模型，换个 harness 跑分可能差得很远，CORE-Bench 就是现成的例子：换了限制更少的 scaffold，同一个模型从 42% 跳到 95%。线上还有分布漂移：用户问的问题，和评测集里的问题，长得不一样。

他们的建议是把自动化评测、生产监控、定期人工审查组合起来用。博客里借用了安全工程里的瑞士奶酪模型：没有单独一层能拦住所有问题，一层漏掉的失败，会被另一层接住。自动化评测拦得住功能回归，拦不住真实用户的奇葩输入；生产监控看得见线上表现，等它报警时问题已经发生了一段时间。所以几种方法要组合使用。

![](/images/articles/2026qiu-agent-bikaoti-eval/fig07.jpg)

— 三片奶酪各开各的孔，没有单独一层能拦住所有问题

「评估的对象是 harness 和模型协作的整体。同一个模型换一个 scaffold，分数就能从 42% 变成 95%。」

还有一个方向性的坑：评测集本身会被污染，裁判模型会被糊弄。评测集混进了训练数据、LLM 裁判被格式化输出骗过，这两个话题展开都是独立的面试题，文末推荐阅读里各有一篇。

业务为什么离不开评测

假设你在一个业务团队，做了一个帮分析师写调研报告的 Agent。内部试用反响不错，团队想推上线。评审会上，领导大概率会问三个问题：它写的东西准不准？比人快多少、错多少？上线之后出了错，谁发现、多快发现？这三个问题没有一个能靠 demo 回答，全部指向评测。

先说迭代权。模型每几个月换一代，提示词天天在改，RAG 策略说换就换。没有评测基线，每次改动都是盲改：你说新版更好，好多少？什么口径？在哪批数据上测的？没有数字，团队只能靠感觉，感觉没法对齐，最后往往是谁嗓门大听谁的。有了一组带基线的对照数字，改版的讨论才能从「我觉得」变成「测出来」。

再说训练侧。在强化学习训练里，评测和训练本来就是一套东西。DeepSeek-R1 训练推理能力时，奖励主要用两类规则：答案对不对、格式对不对。这两类规则本身就是一套评测。

![](/images/articles/2026qiu-agent-bikaoti-eval/fig08.jpg)

— DeepSeek-R1 的规则奖励：答案比对与格式检查汇成奖励分数，评分逻辑本身就是一套评测

最后是验收。企业落地 Agent，最先改变的是谁来负责结果。老板不关心你用了什么框架，关心的是自动化率、错误率、人工复核比例，这些数字从评测体系里来。评测把「模型能力」换算成「业务数字」，换算不出来，AI 能力就进不了 OKR，也进不了预算。

「评测把模型能力换算成业务数字。换算不出来，AI 能力就进不了 OKR，也进不了预算。」

回头看开头那三个问题：准不准，离线评测答；快多少错多少，基线对照答；出错谁发现，生产监控答。一个 Agent 团队招人，要的就是能把这三个问题接住的人。

怎么准备：给项目补上评估数字

分两种情况说。学生和校招的同学，包括找 28 届秋招和 29 届实习的，先别囤新框架。比新框架更有用的，是给手头的项目补上评估数字。Anthropic 的博客里有一句值得记下来的话：「In reality, 20-50 simple tasks drawn from real failures is a great start.」从真实失败案例里抽 20 到 50 条，做成简单任务，就是一个很好的起点。这句话同时回答了两个问题：评测集从哪来（从真实失败来，不从拍脑袋来），评测集多大才够起步（几十条，不是几千条）。

落到你已有的项目上，以最常见的 RAG 项目为例，五个动作：

1\. 固定一个评测集，几十条真实问题，覆盖简单查询和多跳查询；

2\. 定两个指标，检索侧用 Hit@K，生成侧用忠实度；

3\. 跑一遍基线，把数字记下来；

4\. 改一处，换切分策略或者加 rerank，再跑一遍，留下对照数字；

5\. 挑两个失败案例，写清归因：是检索没召回，还是召回了没答对。

这套动作做完，简历上的项目就从「跑通了」变成「测过了」。面试官往下追问每一层，都有数字接。

![](/images/articles/2026qiu-agent-bikaoti-eval/fig09.jpg)

— 当事人称现在就是后悔，非常后悔

在职和社招的同学，重点是把上线验收讲成体系：自动化评测、生产监控、人工审查几层防线，各自拦什么、漏什么，怎么组合；线上出了 bad case，归因顺序是先查评分器，再查数据，最后才轮到怀疑模型。加分的动作是准备一个真实故事：一次指标口径帮你救了业务，或者一次口径选错坑了业务，你发现了什么、改了什么。这类故事背不来，只能来自亲历，所以面试官信。

最后给一个可以直接套用的答题框架。被问「你怎么评估你的 Agent」时，按四步答：

1\. 先定好坏：说指标和基线，不说「效果很好」；

2\. 分层评测：模块级看检索的 Hit@K、MRR，端到端看任务成功率和 pass^k，两条线分开说；

3\. 离线加在线：离线回归管迭代，生产监控管上线，两套口径各自的作用讲清楚；

4\. 主动讲失败：给一个失败案例和归因，这是亲历者才有的证明。

四步走完，面试官基本不会再往深追问，他要确认的东西你已经都给出来了。

SUMMARY

### 🎯 面试总结

回到开场那个场景。面试官连问「怎么测的、基线是什么、离线线上差多少」，是在确认三件事：你有没有评测集、有没有基线对照、有没有线上防线。三者都有的候选人，这一关基本秒过。

三个典型误区：只讲架构不讲评测，RAG、Multi-Agent、Function Call 讲得再流利，问一句「怎么测的」就卡住，说明项目停在 demo 阶段；把「跑通了」当完成，没有评测数字的项目，简历上写不出一个可以核对的指标；低估评测的技术含量，评分器、口径、防线组合，每一层都有坑，评测本身是工程。

模型会一直换，会评估的人一直缺。把「怎么测」讲清楚，这道题就稳了。

阶段 9｜Agentic RL（1–1.5 周）

**学什么：**把「搜索/工具调用」建模成 RL 环境中的动作；交错推理加多轮搜索的训练流程；奖励函数设计与 PPO、GRPO、Reinforce 的选型对比；训练稳定性技巧（retrieved token masking、防止模型走捷径、动态采样与难度过滤、训练数据配比）；veRL、EasyR1、Search-R1 三个框架的技术路线与递进关系。

**动手做什么：**复现 Search-R1，训练一个 3B–7B 的小模型，让它在「思考→触发搜索→整合→回答」的结构里学会何时发起搜索。

**怎么验收：**报告必须包含训练前后模型检索次数与搜索触发位置分布的变化、答案质量（F1/EM）与「引用有效率」的提升、以及 1 到 2 个失败样本的归因和改进思路。比如给一段多步轨迹做归因时，把离线分数和线上表现分开口径记录，先检查评分器判错的样本有没有被修正，再确认模型行为的变化。

**学员案例**（来自社区公开资料）：字节 Seed、腾讯、京东 TGT、蚂蚁 PLAN-A、华为天才少年等录用结果；ICLR、KDD、ICML、NeurIPS、EMNLP、AAAI 等论文录用；USC、杜克、港科大等博士录取。

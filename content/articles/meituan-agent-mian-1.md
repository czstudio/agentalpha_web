**👔 面试官：**先别聊架构。假设你改了一版 prompt，离线评测集上的成功率从 82 涨到 88，你今天就发不发？

**🙋‍♂️ 我：**涨六个点，看着是好事，按理说该发。

**👔 面试官：**那我再给你一条信息。这一版为了涨这六个点，平均每个任务多调了两轮工具，token 烧掉将近三倍，P99 时延从 8 秒顶到 40 秒。你现在还发吗？

**🙋‍♂️ 我：**这个……得看业务能不能忍。要是内部工具，慢点就慢点。要是 C 端，40 秒早跑了。

**👔 面试官：**你这句话才是重点。可你前面那句"涨六个点该发"，说明你脑子里的发布门禁只有一条曲线。我换个问法。你连跑十次，十次都能成一次这样的任务吗？

**🙋‍♂️ 我：**不一定。Agent 是多步的，单步看着都对，串起来偶尔就断在某一步。

**👔 面试官：**对。单步 95% 听着挺高，二十步跑下来还剩多少，你算过吗？为了把成功率顶上去，你打算重试几次，那几次谁买单？

**🙋‍♂️ 我：**……我确实没把重试的账算进去。

这段对话前半段在问"你会不会看指标"，后半段落在一件更实在的事上，一条改动同时动了效果和成本，你怎么判断它是进步还是退步。光把准确率往上拱只是表象，真正的考点是能不能把 token、时延、重试率一起摆上台面，给它们定个预算，再谈涨没涨。下面一层层拆。

### 💡 简要回答

这题我在真实项目里踩过坑，答法分三层。第一层先立一件事，Agent 的可靠性靠每一步相乘出来，省不得。二十步的任务，每步有九五的把握，串下来端到端只剩三成六。想靠重试把整体顶回九成，每步得逼近百分之九十九。

第二层，你为"稳"买的每一次重试，都在计费。单任务的成本是 token（模型计费的最小单位）乘以重试次数，再叠加工具调用往返和等待的时延。效果涨的那几个点，常常正是被重试烧出来的，账单上写得清清楚楚。

第三层，先有成本预算，才谈得上"回归"。发布门禁要同时盯两条曲线，效果线和成本线，给单任务定一个 token 与时延的预算，改动越线就算回归，哪怕分数在涨。同一份算力按题目难度分配，比无脑多跑更划算，评测这一步本身也能省，把裁判从人工换成机器评审，开销能压到人工的零头。

### 📝 详细解析

#### 端到端成功率是每一步相乘出来的，不是平均出来的

![](/images/articles/meituan-agent-mian-1/fig01.jpg)

图：二十步任务每步 95%，端到端只剩三成六；想靠重试顶回九成，每步得逼近 99.5%

一个多步 Agent，每一步都可能错。整体能不能成，取决于每一步都对，这是相乘出来的结果，不是取平均。我常给候选人现场心算这一条。

把单步成功率记作 p，需要连对的步数记作 N，端到端成功率就是 p 的 N 次方。p 取 95%、N 取 20，端到端只剩三成六上下。每步看着都不错，二十步之后十次里成的还不到四次。

单步指标因此很有欺骗性。要把端到端拉到 90%，这二十步里每步得干到 99.5% 左右。这也是业界开始盯 pass^k 这类指标的原因，同一个任务独立重跑若干次全过才算数。τ-bench 的评测里，即便是很强的模型，零售场景上连跑八次全过的比例都不到四分之一。

> 面试时主动把"单步看着高、串起来往下掉"这层点破，比背一个漂亮总分更值钱。

#### 你为了让它稳而加的重试，全都在计费

重试是要计费的，一笔笔直接写进账单。我把单任务成本的口径拆开给面试官看。

一条任务的实际 token 消耗，等于单次尝试的 token 乘以尝试次数。你为了把成功率从 80% 顶到 88%，靠的常常是"失败就整条重来一遍"。多出来的那几个点，几乎全是重试堆出来的。

时延这条线更藏不住。重试把串行链路拉长，工具调用的往返和模型生成是一步步等出来的。前面那道题里 P99（最慢那百分之一请求的水位）从 8 秒涨到 40 秒，多半出在多绕的两轮上，模型本身没变慢。

所以效果分和成本分要一起报。我现在的习惯是给每个任务同时记三个数，token、端到端时延、平均重试次数。少记一个，"涨没涨"这句话就说不圆。

> 把成功率买回来的那笔钱，藏在重试次数里。

#### 时延是另一张账单，用户能直接摸到

成本和时延经常被一起提，却是两种痛。token 花多了月底才知道，时延超标当场就有人骂。

Agent 的时延有两块，一块是首 token 延迟，也就是用户等了多久才看到第一个字；另一块是整条链路的墙钟时间，多步任务里工具调用和模型生成串行叠加。

一个只涨两三个点效果、却把墙钟时间翻倍的版本，放在批处理场景无所谓，放到对话场景就是灾难。所以时延要单独设阈值，别让它躲在平均 token 成本里蒙混过关。

我倾向把 P99 时延当成硬门槛，看平均值容易被骗。任务里简单请求占比高，平均值被大量快任务稀释，看不出问题。用户是被尾部那批慢请求劝退的。

#### 什么时候多花算力划算，什么时候纯属浪费

既然多跑更贵，那到底值不值。哥大的团队在 2024 年那篇讨论测试时算力分配的工作里给了个有用的结论。同样的算力预算，把算力按题目难度聪明地分配下去，比每个题目都跑一堆候选再挑，效率能高出四倍以上。在模型本来就有几分把握的题目上，这么分配甚至能打赢参数量大它十几倍的模型。

分寸要拿捏住。这份收益强依赖题目难度，太难的题上继续往上加预算，改善会打折扣。落到工程上就一句话，别给所有任务统一把重试点满，按难度分档花这份钱。

评测这一环自己也在烧钱。Meta 团队提出的 Agent-as-a-Judge，就是拿一个 Agent 去评另一个 Agent 的产出。他们配套放出一个叫 DevAI 的基准，覆盖五十多个真实开发任务，底下挂着三百多条分层需求。

论文里的成本账很直接，把这一轮评审整个交给机器跑完，花的钱只有人工评审的 2.29%，用的时间是人工的 2.36%。连评测这一步都能靠"机器评机器"省下来，模型侧那点算力就更没有乱烧的理由。

> 算力要花在刀刃上，刀刃就是"有几分把握、但还差口气"的那批任务。

#### 把成本写进发布门禁，别只写通过率

![](/images/articles/meituan-agent-mian-1/fig02.png)

图：τ-bench 的 pass^k 与 pass@k 分叉曲线，同一任务连跑八次全过的比例远低于单次通过（论文 Figure 4，图片来源：arXiv:2406.12045）

落到"今天到底发不发"。我的结论是先把成本从"事后看报表"挪到"上线前设闸门"。

第一件，给单任务定预算。token 预算、P99 时延预算、平均重试次数预算，三个都写进配置。任何一条改动，哪怕分数在涨，只要越了预算线就判回归，回去优化实现而不是先合。

第二件，两条曲线一起看。效果线和成本线画在同一张图上，只报效果就是耍流氓。换模型、改 prompt、加一个工具，全量回归时这两条线都不许变差。

第三件，先在影子流量上验证。新版悄悄跑一遍真实请求，只记录不返回给用户，看清它在真实分布上的成本和时延长什么样，再决定放多少量。这一步能挡掉大部分"离线很绿、上线翻车"。

发布决策是拿效果和成本做权衡，光追单个指标的最大化站不住。你手里得同时握着效果和账单，才谈得上判断一条改动到底值不值。

![](/images/articles/meituan-agent-mian-1/fig03.jpg)

### 🎯 面试总结

回头看开头那段对话，三个典型误区。

第一个误区，把发布门禁想成只有一条准确率曲线。分数在涨就发，是这题最想钓出来的直觉错误。真实世界里效果是收益、成本是账单，一条改动同时动了两者。

第二个误区，把重试当成免费的保险。多跑几次成功率就上去了，听着合理，可每一次重试都在消耗 token、拉长时间，那笔钱实实在在写在月底账单上。

第三个误区，也是最深的那个，是没有成本预算就根本没有"回归"的定义。你不给单任务的 token 和时延设线，就没法回答"分数涨了算不算进步"。把"两条曲线一起看、先在影子流量验、越预算即回归"讲清楚，再带上二十步相乘只剩三成六、重试点满账单翻倍这组标志性数字，这题就稳了。

第 5 章讨论多个 Agent 如何协作完成任务。它适合已经了解单 Agent、工具调用和基本工作流的工程师先学。面试通常不只问定义，还会追问通信、分工、失败处理和一致性。按本章路线准备，建议安排 1-2 天。

## 考点地图

### **通信：Agent 之间传什么**
这一块考消息格式、上下文边界、状态传递和调用关系。面试官会追问谁发起通信、子 Agent 拿到哪些信息、结果如何回传。通信设计决定后面的协作是否可控，也决定上下文是否会快速膨胀。

### **协作策略：任务怎样被拆开**
这一块考串行、并行、流水线和监督者模式的适用条件。面试官会问哪些任务能并行，哪些任务必须等待前置结果。拆分的收益来自上下文隔离和职责分开，代价是通信、调度与结果合并。

### **角色分配：谁负责什么**
这一块考如何定义 Agent 的职责、输入、输出和权限。面试官会追问角色是固定配置，还是根据任务动态选择。角色边界不清时，多个 Agent 会重复工作，或把同一问题反复转交。

### **共识与冲突：结果怎样合并**
这一块考投票、仲裁、验证和状态提交。面试官会追问多个结果不一致时谁有最终决定权，以及同时修改共享资源时如何避免覆盖。共识解决判断差异，冲突解决资源写入和执行顺序，两者不能混为一谈。

## 站内学习路线

### 先打地基

先读 [什么是多智能体（Multi-Agent）？什么时候才需要多个 Agent？](/interview/qa/what-is-multi-agent)，明确多 Agent 解决的不是“人多力量大”，而是上下文稀缺、职责隔离和任务结构带来的工程问题。

接着读 [单 Agent 和多 Agent 怎么选？](/interview/qa/single-vs-multi)，建立选择标准。面试时先判断单 Agent 是否已经足够，再说明拆分后增加的通信、延迟、成本和故障面。

### 再攻高频

按这个顺序刷四篇：

1. [多 Agent 系统怎么通信、怎么编排？](/interview/qa/multi-agent-orchestration)：先掌握消息流、调度关系和结果回传。
2. [多个 Agent 同时改同一个文件，怎么避免冲突？](/interview/qa/multi-agent-conflict)：把抽象协作落到共享资源写入。
3. [子 Agent 崩溃或超时，主流程怎么兜底？](/interview/qa/multi-agent-child-fault)：补上超时、重试、降级和部分结果处理。
4. [多 Agent 系统常见的失败模式有哪些？](/interview/qa/multi-agent-failures)：用失败模式检查前面几块设计是否完整。

这个顺序先回答“为什么拆”，再回答“怎么协作”，最后处理共享状态和异常。本分类 6 篇速答已全部排进上面的路线。

### 最后自测

深度长文用于补充场景判断。先读 [单 Agent 明明能跑，为什么还要拆成 Multi-Agent？](/interview/why-multiagent)，再读 [Workflow vs Agent vs Multi-Agent：自动化层级怎么选](/interview/workflow-vs-agent-vs-multiagent)。长文在补充决策视角，先刷速答，再用长文整理边界。

刷完后进入 [模拟面试抽题](/interview/quiz) 练一轮。答题时固定说明任务拆分、通信方式、角色边界、失败兜底和一致性策略。最后回到 [本分类页](/interview/category/multiagent)，补看遗漏题目。

## 高频追问与避坑

### “为什么不直接用一个 Agent？”
先说明任务是否存在不同上下文、权限或工具边界，再说明拆分后的收益。最后补充通信延迟、状态同步和调试复杂度。只回答“多 Agent 更灵活”，没有给出拆分条件，也没有讲代价。

### “两个 Agent 给出不同结论，系统怎么决定？”
先定义仲裁者或验证步骤，再规定证据、优先级和超时后的默认行为。高风险操作还要把最终提交权限交给受控组件。只说“投票取多数”不够，因为多数结果可能同时错误，也没有处理平票和证据质量。

### “两个 Agent 同时修改同一个文件怎么办？”
先避免直接共享写入，改用任务分片、独立工作区或结构化补丁，再由主流程校验并合并。提交前检查版本、依赖和冲突，失败时保留可重放的变更。只说“加锁”过于单薄，因为锁只能限制并发，不能判断修改是否兼容。

刷完站内内容后，继续做飞书专项真题集，把每道题压缩成定义、机制、代价和场景四步回答。多智能体面试的重点，是证明你知道什么时候拆、怎样协作，以及系统失控时如何收回控制权。
